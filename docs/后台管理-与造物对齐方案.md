## 二、缺口清单（按「用户在后台做不成事」排序）

### P0 · 功能性阻塞

**P0-1 支付链路未打通（充值进不来钱）** ⚠️ 最要紧 ✅ **2026-10-03 已修（口径已修正）**
- 事实：`backend/src/routes/pay/index.ts` 实现了 `GET /channels`、`POST /create-order`、`GET /status/:trade`、`POST|GET /callback/:channel`；但 `core.ts` 的 `ROUTE_WHITELIST` 没有 `pay`，`app.ts` 也没有显式挂载 → **整条链路 404**。
- **口径修正（重要）**：那套 `routes/pay` 属于**旧积分/会员体系**（`o_points_package` / `o_order` / 积分与会员权益），而 XOi 的余额已经是 **new-api quota**，且控制台的充值弹窗本来就是按**网关语义**写的（`POST /api/user/pay {amount, payment_method, top_up_code}` → `{message, data: 表单参数, url: 收银台}`）。
  → 所以**不挂旧支付路由**（那样只会让废弃链路复活），改为**原样代理网关端点**：
  | 新路由（XOi） | 转发到网关 | 说明 |
  |---|---|---|
  | `POST /api/user/pay` | `/api/user/pay` | 下单；失败分支已规整成 `{success:false, message: 真实原因}`（网关原本把原因塞在 data、message 是无意义的 `"error"`） |
  | `POST /api/user/amount` | `/api/user/amount` | 按档位算实付金额（含手续费/折扣） |
  | `GET /api/user/topup/info` | `/api/user/topup/info` | 充值开关 / 档位 / 是否可用卡密 |
  | `POST /api/user/topup` | `/api/user/topup` | 卡密兑换（受合规闸门控制） |
  实现：`backend/src/routes/user/{pay,amount,topup}.ts`，走 `lib/reseller/auth.ts` 新增的 `backendRaw()`（管理员令牌 + `New-Api-User`，**原样透传状态码与响应体**，不改形状）。
- **实测结果**（2026-10-03，真账号）：
  - `GET /api/user/topup/info` → 网关真实返回：档位 `[10,20,50,100,200,500]`、`min_topup=1`、**`enable_online_topup=false`**、**`payment_compliance_confirmed=false`**、`pay_methods=[]`；
  - `POST /api/user/amount {amount:10}` → `{"data":"73.00","message":"success"}`；
  - `POST /api/user/pay` → `{"success":false,"message":"当前管理员未配置支付信息"}`（**接口已通，是网关侧还没配渠道**）；
  - `POST /api/user/topup {key}` → 网关合规提示（`Payment, redemption, ... must confirm compliance terms`）。
- ⚠️ **收钱还差站长在网关后台做两件事**（不是代码问题，也不该代劳）：
  1. 配置支付渠道并开启在线充值（`enable_online_topup=true`、`pay_methods` 非空）；
  2. 确认合规条款（`payment_compliance_confirmed`）—— 兑换码/订阅/邀请奖励同一把闸门。
- 前端同步修好一个真 bug：`recruit.tsx`（招商加盟下单）原先走 `api("/api/user/pay")`，而 `api()` 会按 `data` 解包、**丢掉顶层的 `url`** → 永远落到「暂未开启在线支付」。现已抽出 `console/src/lib/pay.ts`（`requestPay` / `pickScanUrl` / `openCashier`），充值弹窗与加盟页共用同一入口。

**P0-2 内容审核闭环** ✅ **2026-10-03 已验证**
- `GET /api/skills/review`、`GET /api/works/review` 实测返回 `{success:true, data:{items:[], canManage:true}}`（站长账号）—— 列表与权限口径正常，控制台「内容审核」页可用。
- 两个文件头原先写着「必须挂在全局 JWT **之前**」，与事实不符（实际挂在之后，靠 `RESERVED` 放行 `:id` 抢路径），**注释已改正并写清原因**。

**P0-3 兑换码闸门（已知，非代码问题）**

## 三、与造物保持一致的四条原则

1. **机制一致**：菜单三套（new/old/agent）、scope 双闸门（`/api/reseller/me` 下发 scope + `AGENT_PATHS` 前端白名单 + 后端逐接口校验）、role 数值口径（≥10 管理 / ≥100 站长）、legacy 页统一走 `LegacyPage` 壳。
2. **形状一致**：接口沿用造物的 URL 与请求体（`/api/reseller/*` 同构），便于后续把造物的新页面直接搬过来，不用改前端。
3. **差异显式声明**（写进文档，避免后人误判为缺漏）：
   - XOi **没有**独立 React admin（造物 `/adminCenter`），改为 console 内「平台运营」菜单组；
   - XOi **不直接暴露 new-api 用户面端点**，一切走 XOi 后端代理（含两条红线）；
   - 支付走 XOi 自有 `routes/pay`，不是 new-api 的 `/api/user/pay`。
4. **红线不破**（已有决策，别再"顺手补上"）：
   - **不代理 `/api/token/*`** —— 那是签发 sk- 子令牌的端点，代理等于把子令牌发到浏览器，违反「站点级单一令牌」铁律；
   - **不代用户改密码** —— 网关要求用户自己的会话，用管理员令牌代改会变成任意改密路径；
   - `/api/checkin`、`/api/team`、`/api/log/self` 属产品取舍：**建议只做「消费记录」只读代理**（服务端用管理员令牌按 uid 查，不泄露令牌），签到/团队版不做。
