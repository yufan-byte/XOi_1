# 计费透明化与预算方案

> 2026-10-03 · 背景：用户反馈「一直在扣钱」「扣费前想让用户看到多少钱/预算」。
> 本文先讲清现状的扣费逻辑（含真实数据），再给分期方案。

---

## 一、现状：扣费逻辑到底是什么

### 1. 钱在哪里扣

**全部 AI 调用的真实扣费都发生在 new-api 网关侧**，时机是"转发时实扣"（后扣模式）：

```
用户浏览器 → XOi 后端（/api/v1/* 代理 或 画布管线） → new-api 网关 → 上游渠道
                                        ↑
                          这一步实扣「站点级令牌」所属账号的 quota
```

- 站点级令牌（`o_vendorConfig.newapi.inputValues.apiKey`，tokens 表 id=1，令牌名「测试」）**挂在站长账号（cheny / user 1）名下**；
- 所以**所有人的生成消耗，都从站长的网关余额里走** —— 这就是「一直在扣钱」的直接原因：你不是在被系统扣，是每一次生图/视频/Agent 对话都在真实消耗网关额度。

### 2. 实测单价（今天 7 笔真实账单，网关 logs 表）

| 调用 | 模型 | 实扣 | 折合 |
|---|---|---|---|
| **视频一条**（5 秒 720P） | agnes-video-2.5-flash | 46,875,000 | **¥93.75** |
| **Agent 一轮对话** | agnes-2.0-flash | ~523,500 | **~¥1.05** |
| 短对话 | agnes-2.0-flash | ~11,000 | ~¥0.02 |
| **今日合计** | 7 笔 | 94,823,327 | **¥189.65** |

换算口径：网关 quota ÷ 500000 = 元。

### 3. 两个「感觉不合理」的真相

**① 本地积分价和真实成本严重脱节**

| 动作 | 本地积分价（o_points_price） | 网关实扣 |
|---|---|---|
| video_generate | 20 积分 | **¥93.75** |
| image_generate | 5 积分 | （按图模/尺寸浮动） |
| text_generate | 1 积分 | ~¥1（Agent 大 prompt 一轮） |

本地积分是早期拍脑袋定的行价，**既没跟上网关倍率，也区分不了参数**（5 秒和 10 秒、720P 和 1080P 同价）。用户看到的「20 积分」和实际扣的「¥93.75」对不上，这是信任问题的根源。

**② Agent 对话为什么一轮就 ~¥1**：创作 Agent 的 system prompt 带画布上下文 + 工具定义 + Skill 正文，输入 token 很大；flash 级模型也架不住轮轮大输入。这不是 bug，但用户完全无感知。

### 4. 不用担心的事

- 计费是**后扣模式**：`reservePoints` 只做余额软校验（管理员放行不扣），本地不产生扣费流水（`o_points_ledger` 恒空属预期）；
- 管理员（你）目前**不消耗本地积分**，但网关额度是实打实在扣的；
- 失败任务不产生网关扣费（网关只对成功转发的 token/时长计费）。

## 二、方案：扣费前让用户看到多少钱

### 设计原则

1. **价格唯一权威是网关**（渠道倍率 × 模型价），本地只做折算展示，不再维护第二套价目表；
2. **大额强制确认，小额静默**：视频（¥90+）必须弹确认，图片/对话（<¥5）常显单价即可，别把用户烦死；
3. **预算是承诺不是预估**：报价端点给出的数字要能对上账单（±10% 内），做不到的参数（如 LLM 按实际 token）明确标注「预计」。

### P1 · 报价透明（先做，1 个端点 + 2 处 UI）

**统一报价端点** `GET /api/billing/quote?action=&model=&seconds=&resolution=`

- 数据源：网关 `abilities` 表的 model_ratio / model_price / completion_ratio（有 `/api/pricing` 就走它，没有就直查同库 abilities —— 业务库和网关**同库**，零代理成本）；
- 返回：`{ amount_yuan, points_display, price_basis }` —— 视频按秒数×档位能算准；图片按张×尺寸算准；LLM 标注「按实际 token 结算，预计 ~¥X/轮」；
- 后端缓存 60s，防刷。

**前端两处**

1. **提交前确认卡**（画布节点 / 创作Agent 的生成动作）：
   > ┌ 预计消耗 ────────────┐
   > │ 视频 5秒·720P    **¥93.75**  │
   > │ 余额 ¥X → 预计剩 ¥Y        │
   > │ ☐ 本次会话不再确认          │
   > │        [ 取消 ] [ 确认生成 ] │
   > └─────────────────────┘
   触发条件：`amount_yuan ≥ 5`（阈值可配）强制弹；低于则只在按钮旁常显「≈¥0.02」。
2. **按钮旁常显单价**：生成按钮下方一行小字「视频 ≈¥93.75/条（5秒·720P）」，参数变了实时刷新（调 quote 端点）。

**顺带修正本地积分价**：o_points_price 的 video_generate 20 → 按 quote 折算展示「≈¥93.75」，两套数字合并成一个来源，别再各说各话。

### P2 · 预算控制

- **单次预算**：报价超余额 → 后端直接拒绝（现在 reservePoints 已拦 quota≤0，补上「quote > 剩余」的提前拦截，别让任务跑完才发现扣超）；
- **每日预算上限**（可选，用户自设，默认不设）：存 `o_user` 新列或 o_setting，`reservePoints` 软校验处加当日累计（查网关 logs 当日 SUM，同库一条 SQL）；
- 超限报错文案给足信息：「今日已消费 ¥X / 上限 ¥Y，明天恢复或到设置里调高」。

### P3 · 账单对齐（信任闭环）

- 消费记录页（已有 `/api/log/self` 代理）补**按天聚合**：日期、次数、分模型金额；
- Agent 对话在消息气泡角落显示该轮实际消耗（轮询结束后从网关 log 按 request_id 回捞）——让「为什么一轮 ¥1」可见；
- 站长侧「平台运营 → 充值记录」已有，加一列「分用户归属」（见下）。

### 附带一个架构提醒（与预算无关但必须知道）

现在是**全站共用站长的一个网关令牌**：任何用户的生成都在扣你的余额，本地积分并没有真正"花出去"。将来对外开放注册后，要么：
- a) 每用户在网关建子令牌（违反「不代理 /api/token/*」红线，不可取）；
- b) 保持站点令牌 + 本地积分**真扣**（把现在的软校验升级为真扣账本，网关消耗按 log 归摊到用户）——推荐，P2 的预算控制正好搭在同一套数据上。

## 三、落地顺序与工作量

| 阶段 | 内容 | 改动面 |
|---|---|---|
| P1 | quote 端点 + 确认卡 + 按钮单价 + 积分价对齐 | 后端 1 路由（同库查 abilities）+ 前端画布/Agent 两处 UI |
| P2 | 超额拦截 + 每日预算 | billing.ts 软校验处 + 1 个用户设置项 |
| P3 | 账单聚合 + 对话轮次消耗展示 | 消费记录页 + Agent 前端 |

P1 做完，用户就能在每次扣费前看到准确价格；P2 防失控；P3 补信任。
