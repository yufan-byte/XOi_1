# XOi 商业化支付与积分上线计划

## 结论

采用“XOi 自有账务核心 + 支付渠道适配器”的混合方案。

- XOi 自己负责用户、订单、积分、会员、退款、对账和审计；
- 支付宝、微信只负责支付下单、支付查询、退款和回调验签；
- 不把积分余额或会员权益交给第三方支付框架管理；
- 开发环境保留模拟支付，生产环境只允许已配置并通过健康检查的真实渠道。

这样可以避免支付框架的订单模型绑死 XOi，也方便未来增加 Stripe、企业转账或其他渠道。

## 当前已完成

- 支付渠道抽象：支付宝、微信、聚合渠道、模拟渠道；
- 订单快照：金额、积分、赠送积分、会员等级和有效期；
- 支付回调验签入口；
- 支付回调金额校验；
- `pending -> paid` 的并发幂等状态转换；
- 积分扣除事务和余额不足保护；
- 充值积分关联订单二次幂等；
- 会员权益与支付订单同事务发放；
- 生产环境禁止模拟支付；
- 生产环境禁止普通管理员直接修改会员权益；
- 开发环境和生产构建检查。

## 必须完成的账务升级

### 1. 订单金额统一使用整数分

现有金额字段仍兼容元制浮点数。正式上线前应增加整数金额字段：

```text
amount_cent INTEGER NOT NULL
```

历史 `amount` 字段只用于兼容读取，新的订单、回调和退款全部使用 `amount_cent`。

### 2. 增加积分账户和账本

建议增加：

```text
o_points_account
- user_id
- balance
- frozen_balance
- version
- updated_at
```

```text
o_points_ledger
- user_id
- amount
- balance_after
- type
- reference_type
- reference_id
- idempotency_key
- operator_id
- created_at
```

`o_user.points` 暂时保留作为兼容和查询缓存，但所有新业务都通过账户服务修改余额。

### 3. AI 消费改成冻结、确认、释放

```text
创建任务 -> 冻结积分 -> AI成功确认扣除
                         -> AI失败释放积分
```

每个任务必须有唯一 `idempotency_key`，避免用户重复点击、网络重试或 WebSocket 重连造成重复消费。

## 正式支付流程

```text
选择套餐
  -> 后端读取套餐并生成订单快照
  -> 创建 pending 订单
  -> 调用真实支付渠道
  -> 前端展示二维码或支付参数
  -> 渠道异步回调
  -> 验签、校验商户号、订单号、金额和渠道
  -> 事务锁定订单
  -> 发放积分/会员权益
  -> 记录账本和支付流水
  -> 返回渠道成功回执
```

不得根据前端“支付成功”页面直接发放权益，必须以服务端回调或服务端主动查询结果为准。

## 退款与对账

需要增加：

- `o_refund_order` 退款单；
- 退款申请、审核、处理中、成功、失败状态；
- 原订单金额和退款金额校验；
- 退款成功后按规则回收未使用积分或冻结账户；
- 每日下载支付宝/微信账单；
- 平台订单与渠道账单自动对账；
- 差异进入人工处理队列；
- 所有补单、退款、人工赠送必须记录操作人和原因。

## 会员生产化

会员套餐应从积分套餐中独立出来：

```text
o_membership_plan
- name
- level
- duration_days
- price_cent
- included_points
- daily_generation_limit
- concurrent_task_limit
- storage_limit
- enabled
```

会员购买仍然复用统一支付订单，但权益由会员服务发放。会员有效期采用续费叠加策略，升级、降级、退款和到期都通过状态机处理，不能由前端直接修改等级。

## 上线前测试清单

- 同一订单重复回调 10 次，只发放一次；
- 两个并发回调，只发放一次；
- 回调金额少 1 分时拒绝入账；
- 回调订单号不存在时拒绝入账；
- 支付成功但权益发放异常时可重试；
- AI 任务失败时积分完整释放；
- AI 任务超时后不会永久冻结积分；
- 用户不能查询和操作其他用户订单；
- 生产环境无法使用模拟支付；
- 退款不会重复扣回或重复返还；
- 价格修改不会影响历史订单；
- 数据库和 OSS 备份可恢复；
- 支付密钥不会进入日志、Git 或前端响应。

## 实施顺序

1. 金额字段迁移为整数分；
2. 增加积分账户、账本和幂等键；
3. AI 消费接入冻结/确认/释放；
4. 增加退款单和人工补偿；
5. 增加支付宝/微信生产配置健康检查；
6. 完成正式支付沙箱测试；
7. 增加每日对账和异常告警；
8. SQLite 迁移 PostgreSQL，任务和支付锁接入 Redis；
9. 压测后灰度上线；
10. 观察账务和支付数据后再开放全量用户。

## 技术路线选择

当前不直接接入一个“大而全”的第三方支付框架。最适合 XOi 的方式是：

1. 保留现有支付渠道接口；
2. 使用支付平台官方 SDK 或官方 API 完成签名、下单、查询和退款；
3. XOi 自己维护统一订单和权益发放；
4. 每个支付渠道单独实现并可替换；
5. 所有渠道最终都调用同一个 `fulfillPaidOrder` 和账本服务。

原因是 XOi 的核心不是“收款页面”，而是积分和会员权益的准确记账。第三方框架可以减少签名代码，但不能替代 XOi 的账务模型、并发控制和审计责任。
