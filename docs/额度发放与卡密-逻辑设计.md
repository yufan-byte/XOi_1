# 额度发放与卡密 · 逻辑设计

> 触发问题：「管理员的后端没发增加卡密 / 给用户发钱，合理吗？」
> 结论：**不合理，两处都缺**——卡密是被一条错误的校验卡死，额度发放是压根没有入口。本文定口径。

---

## 一、先把「谁给用户加钱」拆成三条路

平台给用户加余额，一共只有三种正当姿势。**它们不是替代关系，是不同场景各用一条**：

| | 在线充值 | 卡密（兑换码） | 额度发放（本次新增） |
|---|---|---|---|
| **谁出钱** | 用户自己扫码付 | 平台发行（代理发码则代理先按面值买断） | 平台 |
| **凭证形态** | 无（直接到账） | 一次性可流通码 | 无，直接改余额 |
| **适合场景** | 用户主动买算力 | 对外售卖、活动分发、批量给不特定用户 | 客服补偿、误扣回滚、活动奖励、内部测试 |
| **用户操作** | 下单支付 | 拿到码后自己兑换 | 无需操作，客服点一下就到位 |
| **留痕** | 网关 topup 表 | 网关 redemption 表（有核销状态） | `o_quota_ledger`（type=admin，记原因/操作人） |
| **状态** | ✅ 已通（等站长配支付渠道） | ✅ 已通（受合规闸门管） | ✅ 本次新增 |

**关键区分：**
- 要「对外售卖 / 批量分发 / 需要可流通凭证」→ 用**卡密**。
  它的好处是码可以转手、有核销状态、发出去还没被兑换时可以先撤销（禁用）。
- 要「点对点补一个人」→ 用**额度发放**。
  拿卡密来做点对点补偿是**反模式**：为了补 3 块钱要发行一张可流通凭证，码还会留在兑换码库里等被核销，既不精确也不安全。

## 二、本次修掉的两个问题

### 问题 1：站长发不出卡密（错误校验）

**现象**：站长点「批量生成卡密」，只要面额合计超过自己钱包余额就被拒（报「代理钱包余额不足」）。

**为什么错**：XOi 的账户体系里，**用户余额 = new-api 的 `users.quota`**，站长自己也是一个用户。
而「卡密」是**平台发行的负债凭证**——发行方不需要先拥有这笔钱，它是给用户记的账。
代码在 platform 分支里照抄了 agent 分支的「钱包扣款」判定：

```
if (scope.kind === "agent") { ...从代理钱包按面值扣款... return; }   // ✅ 代理：他是转售方，必须先买额度
...
if (toCny(u.quota) < amount * count) return fail("代理钱包余额不足");  // ❌ 站长：他没理由被自己的钱包卡住
```

代理那条是对的（代理是转售方，先按面值从自己钱包买断，再转卖；失败要退款），
但站长这条是**语义串台**。实测站长余额 ¥200 时，发 ¥300 的码直接被拦——而这条路本来就该畅通。

**修法**：平台分支去掉钱包校验，只留「单批面额合计 ≤ ¥100000」的防手滑上限。
前端 `CardKeysTab` 同步：站长看到的是「平台发行 · 不扣钱包」，不再显示/校验钱包余额。

### 问题 2：没有「给用户发钱」的入口（新增能力）

**新增** `POST /api/admin/credits`：按 `用户ID 或 用户名` 精确指定目标，加/减额度，**必须填原因**。

设计要点（每一条都是为了「动钱这件事不能含糊」）：

| 约束 | 为什么 |
|---|---|
| 只有 **role ≥ 100（站长）** 能提交 | 普通管理员（10–99）看得到记录，但动不了钱；前端隐藏按钮不算数，后端再查一次 `users.role` |
| **原因必填**（2–200 字） | 这是给用户账户加钱的高影响操作；原因会永久写进审计流水，对账时能追溯 |
| 单笔 ≤ ¥100000 | 挡住手滑多按两个零 |
| 扣回**先校验余额** | 只扣得动当前余额，扣不穿（不把用户余额做成负数） |
| 写 `o_quota_ledger`（type=admin，operator_id=操作人） | 复用全站唯一的额度账本，不另建表。记录形状：谁、给谁、多少钱、为什么 |
| 目标用户必须存在 | 用户名精确匹配或数字 ID，找不到直接 404，不做模糊猜测 |

**为什么复用 `o_quota_ledger` 而不是新建表**：`utils/quota` 的 `applyQuotaChange()` 已经是全站唯一的额度写入口（充值 / 赠送 / 签到 / 返还都走它），它自带 `type + description + operator_id` 三个审计字段。把 type 固定成 `admin` 就是一张现成的发放台账。

## 三、顺带挖出的严重隐患（已修，影响全站到账）

排查「额度发放」为什么报错时，发现**网关的额度接口契约一直是错的**：

```
❌ 旧代码：POST /api/user/manage { id, action: 1, value, mode }        → {"success":false,"message":"Invalid parameters"}
✅ 正确：  POST /api/user/manage { id, action: "add_quota", mode: "add"|"subtract"|"override", value: 正整数 }
```

`action` 是**字符串动词**（同族还有 `enable` / `disable` / `promote` / `demote` / `delete`），不是数字枚举。
网关遇到非法入参时 **HTTP 仍返回 200**，只在 body 里写 `success:false` —— 所以这个错误一直没被当成错误。

**影响面**：`utils/newapi.ts` 的 `adjustQuota()` 是全站唯一的额度写入实现，
充值回调、新用户赠送、签到、返还……**全部到账失败**。之所以一直没暴露：在线充值未开（`payment_compliance_confirmed=false`）、签到未开、本地也几乎没人注册，这条路径从来没被真正走到过。

**修法**：`adjustQuota()` 改用正确契约；顺带修掉同错法的 `adminSetUserStatus()`（`action:"enable"/"disable"`，原先误写为 `action:1 + status`，同样是死代码级的隐患）。

**实测**：`add 5000 → 余额 +5000`、`subtract 5000 → 余额 -5000`，净变动 0，精确生效。

## 四、边界（别越线）

- **合规条款由站长本人确认**（不要替他勾）：兑换码的开关由网关侧 `payment_compliance_confirmed` 与 `enable_redemption` 管。
  2026-10-03 起**已按站长明确要求**在本机网关确认（`POST /api/option/payment_compliance {confirmed:true}`，需 access token，
  见 `docs/画布模型与网关统一.md` 旁注）→ `enable_redemption=true`，卡密已可正常下发。
  仍待站长处理的是**支付渠道**（`enable_online_topup=false`，需要真实收款账号/密钥）。
- **不代理 `/api/token/*`**：站点级单一令牌红线，额度发放只动 `users.quota` 一列。
- **不改用户密码**：与本体系无关的动作一律不做。
- **发放不能"隐身"**：任何绕过 `o_quota_ledger` 的加钱写法都不接受——没有留痕的动钱等于没有账。

## 五、验证清单（已跑通）

1. `GET /api/admin/credits` 空态 → `[]`
2. 发放 ¥0.50 → 余额 200.00 → 200.50（**真实变动**）
3. 扣回 ¥0.50 → 余额回到 200.00
4. 记录 2 条，字段含 用户 / 变动 / 变动后余额 / 原因 / 操作人
5. 缺原因 → 400；超 ¥100000 → 400；目标不存在 → 404
6. 站长发 ¥300 卡密：**越过钱包闸**，只剩合规闸（符合预期，等站长确认条款）
