# 渠道成功率与选线策略（对标造物）

> 起因：用户在造物「选择渠道策略」面板看到一列「成功率 · 暂无数据」，问这套数字怎么来的、
> 点「稳定优先 / 价格优先 / 速度优先 / 手动选线」到底改变了什么，并要求我们同步。

---

## 1. 造物是怎么拿到成功率的

不是自己算的，是**抓外部面板**：

| 环节 | 事实（源码依据） |
|---|---|
| 数据源头 | 上游 `aicost` 的「请求成功率」面板 |
| 采集 | 宿主机任务 `ops/line-health` **每 5 分钟**把整份面板落盘 |
| 中间层 | `src/lib/line-health.ts`：`{ updated_at, window_minutes:120, bucket_minutes:5, lines:{<上游线路名>:{category,rate,avg,buckets[]}} }` |
| 下发 | `GET /api/line-health`，**只给登录用户**；并用 `soldLines()` 只保留「站内渠道真在卖」的线路（渠道 `models` 经 `model_mapping` 换成上游名后的集合）—— 审计 D-12 的原因：匿名能拿到全部上游线路 id 与成功率 |
| 前端 | `src/components/media/line-health.tsx`：24 个 5 分钟点阵，`rate>=95` 绿 / `>=60` 黄 / 其余红 / `-1` 灰；**超过 20 分钟没更新就当作没有数据** |

所以截图里满屏「暂无数据」不是坏了，是那 54 条线路在 aicost 面板里确实没有请求记录（或数据过期）。
造物的取舍很明确：**宁可不显示，也不摆假数字**。

## 2. 点「稳定 / 价格 / 速度 / 手动」之后改变了什么

面板本身不改上游，改的是**候选线路的取用规则**：

| 策略 | 排序规则 |
|---|---|
| 稳定优先 | 按成功率降序，同分比价格 |
| 价格优先 | 最便宜的优先（造物要求成功率不低于阈值，否则会选到死掉的便宜线） |
| 速度优先 | 按平均耗时升序 |
| 手动选线 | 不自动排，用户勾选/点选哪条用哪条 |

三件事同时发生：

1. **列表按策略重排**，第一行就是「将使用」的线路（面板底部那行文案）
2. **勾选框 = 收窄候选池**：勾了就只在这些线路里择优，不是全局最优
3. **锁定后不自动换线重试**：命中一条线就钉住，失败直接报错，避免换个线路重试导致重复扣费

## 3. 我们已经有的 & 缺什么

`frontend/console/src/one-stop/video-studio.tsx` 里早就有同款 `ChannelStrategy`
（4 个策略 + 线路表 + 成功率高/耗时/价格 + 锁定勾选）。对照后有两个真问题：

| 问题 | 原来 | 现在 |
|---|---|---|
| 成功率粒度不对 | `/api/model-health` 只按**裸模型名**从站内任务记录聚合近 24h —— 同一模型下的多条渠道共用一个数字，排序等于没排 | 新增 `/api/model-lines`：直接读网关 `logs`，按 **(渠道 × 模型)** 聚合，窗口 120 分钟、5 分钟一个桶 |
| 策略不生效 | 选「稳定优先」只把表排了序，底部写一句「将使用」，用户不点「改用」什么都不变 | 切换策略立即应用最优档位（`manual` 除外），并用 ref 去重，避免刷新时把用户手挑的档位顶掉 |

另外加了**最小样本保护**：少于 3 次请求的成功率不参与排序（1 次成功算 100% 会把「稳定优先」带沟里），
但仍显示数字并标注「样本太少，不参与排序」。

## 4. `/api/model-lines` 设计

```
GET /api/model-lines?window=120&model=<可选>
→ { updatedAt, windowMinutes, bucketMinutes, models: {
     "<model>": { ok, fail, health, avgSec, buckets[24], source, lines: [
        { channelId, channelName, channelStatus, ok, fail, health, avgSec, buckets[24] }
     ]} } }
```

- **主数据源**：网关 `logs`（`type=2` 消费成功 / `type=5` 错误，`created_at` **是秒不是毫秒**），join `channels` 拿渠道名
- **回退**：画布/一站的部分媒体任务走 `/v1/canvas` 适配层，不落网关日志 → 用 `xoi_generation_tasks` 补，
  并标 `source:"tasks"`、线路名写「站内任务记录」，不让用户误以为是渠道级数字
- 桶里没请求记 `-1`；`health` 无样本时为 `null`（不编 0% 也不编 100%）
- 独立只读小池（`max:3`）连网关库，不和业务库抢连接；`Cache-Control: no-store`

验证（`curl /api/model-lines`，本机真实数据）：

```
glm-5.3-flash        gateway health=100  n=4  avg=29.8s
doubao-seedream-5-0  gateway health=50   n=2  avg=55s
deepseek-v4.1-flash  gateway health=100  n=5  avg=46s
```

## 5. 我们的「线路」和造物不完全等价（必须讲清楚）

造物的 54 条线路 = **同一条能力的 54 台上游**，可以钉死用哪台。
我们的渠道是 new-api 按 `priority` / `weight` 自动调度，**前端钉不住某条渠道**。

所以我们的策略实际决定的是**档位（模型）**：同系列里哪个更稳/更便宜/更快。
面板里每条模型背后的渠道健康度摊开给它看（`N 条渠道` 的 title 里有逐条成功率），
但「锁定」锁的是档位，不是上游。

要做到真正钉渠道，需要改 new-api 的渠道优先级/权重，或走「指定渠道」头 —— 那是另一个改造。

## 7. 能不能直接把造物的数据拿过来（2026-10-27 实测）

### 7.1 结论：能读，但**不能当我们的成功率用**

实测（用 `backend/.env` 里的 `ZAOWU_LOGIN_*` 账号，只读一次）：

```
登录 zwyq.ccdan.live         → 200，拿到 token
GET /api/line-health         → 200
窗口 / 桶                    → 120 分钟 / 5 分钟，updated_at 只比当前晚 5 分钟
线路数                       → 32 条，条条有数（rate 47.4 ~ 100，avg 179 ~ 2628 秒）
```

**技术上完全可行**，一条 token 就能拿到。但关键的一步没通过：

```
我方 SKU                     命中情况
seedance2.0-line1-xoi        未命中
seedance2.0-line1-fast-xoi   未命中
seedance2.5-line1-xoi        未命中
```

他们那 32 条是**上游线路名**（`seedance2.0-900-3` / `seedance2.5-kk-720p` / `seedance2.0-fast-2`…），
我们买的是他们**打包后的商品名**（`*-line1-xoi` 后缀）。两套名字体系不通，
请求时是我们的 SKU 原样发过去、他们内部再用 `model_mapping` 换成上游名 —— 那张映射表在对方手里。

### 7.2 为什么不该拿它当展示口径

| 问题 | 后果 |
|---|---|
| key 对不上 | 32 条线路无法归到我们的 SKU，展示只能整体平均 → 数字没有意义 |
| 口径不同 | 它反映「aicost 那条上游线稳不稳」，我们要回答「我们卖的这条 SKU 稳不稳」 |
| 延迟叠加 | 他们自己 5 分钟抓一次、20 分钟过期；我们再套一层，最差 25 分钟 |
| 耦合 | 依赖对方账号登录、接口不变、不做风控；对方一改 filter 就整片空白 |
| 数据边界 | 那是对方业务数据，长期依赖不合适 |

最坏的情况是：面板显示 98%，但我们这条 SKU 这周一直在报错 —— 用户会认为我们在造假。

### 7.3 可以用，但只能当「上游预警」

真正有价值的地方是**冷启动先验**：我们自己样本少（视频类尤其），而他们 32 条条条有数。
如果能建立 `SKU → 上游线路` 对照，就可以：

1. 每 5~10 分钟拉一次（**必须复用 token 缓存**，别每次登录 —— new-api 并发会话有上限，
   参考 `lib/workspace/imageRecover.ts` 里 13 分钟缓存 + in-flight 合并那套）
2. 命中「某条上游线路最近持续低成功」→ 对我们对应 SKU 临时降权 / 提示 / 熔断
3. 只在**内部**可见（管理端 / 运营页），不进用户侧成功率字段

### 7.4 卡在哪一步、需要什么

**缺一张对照表**：`seedance2.0-line1-xoi` 背后到底是 `seedance2.0-900-3` 还是 `seedance2.5-900`。

三条路（按成本从低到高）：

1. **问造物要**：让他们给一份「我方 SKU → 上游线路名」的 model_mapping（最干净，一句话的事）
2. **看商品详情**：他们商品页/接口里若标了对应上游线，抄下来建静态表
3. **不要映射**：只把 32 条线路整体当「上游雷达」看，用于内部告警，不落到具体 SKU

在拿到映射之前，做预警层是空转 —— 所以先不动手。

## 8. 一站式音频工作台与造物的差距（2026-10-27）

### 8.1 已修：参数胶囊不再折叠（"我们的不会随模型变"）

其实**前端一直是 schema 驱动的**：选中豆包语音合成 2.0 会出现「情绪 auto / 情绪强度 4」，
换海螺 2.8 会出现「档位 / 变声 / 情绪 / 版本 / 音效」。问题出在 `ParamPills` 的 `maxInline` 默认 3 ——
多出来的参数被塞进「更多参数 5」的折叠里，光看输入框根本看不出差异。

`audio-studio.tsx` 里 `maxInline={8}`：海螺 2.8 现在摊开 8 个胶囊
（音色 / 语速 / 格式 / 档位 / 变声 / 情绪 / 版本 / 音效），与造物一致。

### 8.2 已修：提示词大师不该出现在音频输入框

`media-page.tsx` 里那个按钮是无条件渲染的。音频（配音、音色克隆）没有"画面描述"可优化，
造物那边音频输入框只有「智能帮写」。已加 `modality === "image" | "video"` 判断。

### 8.3 待办：音色克隆 / 音色设计（上游有，我们没上架）

实测 `abilities` 表里上游**是有的**：

```
voice-clone     ← 海螺 音色克隆（sample_url + voice_id + preview_text）
voice-design    ← 海螺 音色设计（prompt + preview_text + voice_id）
```

但 `lib/model-catalog/index.ts` 的 `selectable` 把它们主动排除了：

```ts
const specialty = /superres|lip-sync|avatar|voice-clone|voice-design|repaint/i.test(modelName);
selectable: meta.available !== false && !specialty && (type !== "audio" || /tts|speech/i.test(modelName))
```

要上架需要三件事：① 放开这两条过滤；② 音频工作台加「上传音频」格子（`sample_url` 走
`/api/canvas-files` 拿站内地址）+ `voice_id` 自动生成；③ 定价口径（造物是"克隆一次性收音色费，
之后按字数合成"）。**属于产品决策，没有擅自上架。**

### 8.4 发现的真问题：模型目录同步长期失败

前端能随模型变，但**参数目录本身是旧的**。`.xoi-run/backend.log` 里有 1243 条同样的错误：

```
[upstream-sync] 保留当前价格： 同步 billing_setting.billing_expr 失败：
Invalid billing expression for model grok-imagine-video:
plugin xai: usage key "billing_aspect_ratio" is not declared by the task plugin
```

`startUpstreamPricingSync()` 每 15 分钟跑一次，每次都整批失败 —— 因为 new-api 是按**模型**校验
计费表达式，`grok-imagine-video`（以及一批 `seedance*` 促销档，报 "has no task plugin usage schema"）
不兼容当前插件版本，只要它在 payload 里，整份 option 就被 400 打回。
于是 **ModelRatio / 参数卡片 / 价格全部停在旧快照**，只有 `status='synced'` 的旧 snapshot 被读到。

尝试过的修法（已回退，未上线）：按错误信息把被拒模型剔掉再重试。
实测无效 —— 剔除后重试仍然报同一个模型，说明 new-api 是拿**库里的模型清单**校验，
不是只看 payload。要真正解决只能二选一：

1. **拉黑不兼容的模型**（`grok-imagine-video` + 那批 seedance 促销档）—— 等于不卖它们，需产品确认
2. **升级 / 修 new-api 的 xai 任务插件**，让它认识 `billing_aspect_ratio` / `billing_resolution` 这些 usage key

顺带修好的一处（已保留）：`cards.ts` 之前只保留 `enum`、把上游的 `options` 中文标签丢了，
导致界面上出现 `hd` / `none` / `auto`。现在保留 `label` / `description`（只收展示文案）。
**但要在同步跑通之后才会生效** —— 受 8.4 阻塞。
