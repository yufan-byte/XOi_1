# XOi：分析助手、画布 Agent 与 175 个 Skill 接入方案

初版：2026-10-09；切换体验更新：2026-10-10。依据 XOi、造物源码和本地购买包检查；工具可用性不能仅凭文件存在判断。

## 1. 产品分工与本次实现

建议保留两个明确入口，共用模型网关与 Skill 索引，但分别授予工具权限：

| 入口 | 用户任务 | 执行权限 | 交付 |
|---|---|---|---|
| 分析助手 | 聊天、创作构思、参考视频拆解、提示词方案 | 本轮视频的 `analyze_video`；没有生成、画布写入、网络搜索或脚本权限 | 文字分析、时间戳抽样图、制作方案 |
| 画布创作 | 根据方案组织节点、生成图片 / 视频、编辑资产 | 使用既有画布入口与生成服务；具体权限仍由各画布服务校验 | 画布节点和媒体资产 |

本次已实现主站两个入口、分析助手后端工具白名单、视频抽帧分析、执行状态、停止按钮、失败提示、对话历史和“将此方案带入画布”。选择“画布创作”使用原有画布交接；选择“分析助手”留在主站聊天。切换入口保留当前分析对话和抽样图，不新建、不清空，也不调用模型。两个工作区各自保留未发送文字、附件、技能选择和模型偏好。

这是独立的分析执行入口和权限边界，不要求再购买一个模型：同一个模型可在不同 Agent 中接收不同工具集合。画布已有服务没有被整体重写；统一所有旧画布接口的权限策略属于后续工作。

### 使用步骤

1. 打开主站智能创作，选择“分析助手”；普通文本也可以直接发送。
2. 在分析助手选择一个同时支持 **工具调用和图片输入** 的聊天模型。默认模型不保证支持；不支持时会明确报错。
3. 从“素材”上传一个视频，或选择素材库视频，点击“抽帧分析”。没有问题时补上默认分析问题；此按钮会调用模型。普通切换按钮只切换工作区。
4. 查看 12 张带时间戳的抽样画面与分析结果，可继续追问。
5. 点击某条成功回复的“将此方案带入画布”，在画布审核方案、选择生成模型并继续制作。交接本身没有调用生成模型。

### 视频能力边界

- 浏览器对整个视频均匀抽取 12 帧，包含开头与结尾区域；长视频不会只取前几分钟。
- 单个本地视频最多 100MB，时长最多 30 分钟，每轮分析一个视频。JPEG 长边最多 640 像素。服务端验证 2–16 帧、真实图片解码、时序和大小，拒绝 URL 作为抽帧输入。
- 原视频不上传给分析后端；JPEG 抽样图发送给当前用户的模型网关。前端保留原文件的临时 Blob 地址，避免把大视频编码进聊天 JSON。
- 输出基于抽样画面的内容、主体、构图、色彩、叙事推测与复刻提示词。**不读取音轨、不做精确逐镜头检测**；运镜和镜头边界只能作为推测。
- 远程素材需要允许浏览器跨域读取，编码需受浏览器支持；失败时提示用户下载后本地上传。
- 视频分析最多调用三次模型：工具规划、视觉分析、最终回复。调用实际网关模型会消耗账号用量；停止操作可以取消后续请求，已开始的网关调用仍可能结算。
- 抽样图不保存到 localStorage 对话历史；文字报告可以恢复，恢复的历史不包含抽样图。
- 普通画布草稿交接保持 4MB 附件上限。视频分析成功后移除分析区已消费的视频附件；失败保留附件供重试。“将此方案带入画布”只交接选中的文字方案，不附带未发送附件，不受失败视频大小限制。

### 切换规则（2026-10-10 已实现）

用“要做什么”决定工作区，不让模型自动更换 Agent 或自动执行制作：

| 用户动作 | 行为 | 会调用模型吗 |
|---|---|---|
| 点“分析助手” | 恢复分析草稿和原对话，可继续聊；画布草稿留在画布入口 | 否 |
| 点“画布创作” | 恢复制作草稿、附件、技能和模型；分析结果留在分析入口 | 否 |
| 在画布入口点“抽帧分析” | 将本轮视频复制到分析区，保留画布原素材；合并分析草稿与当前需求，执行分析 | 是 |
| 分析区已有附件时，从画布点“抽帧分析” | 先切到分析区并提示处理已有附件，保留双方草稿，避免静默替换参考视频 | 否 |
| 点分析区“发送” | 发送文本或本轮视频，携带最近有效对话上下文 | 是 |
| 点某条“将此方案带入画布” | 只交接这条文字方案；使用画布区模型偏好，进入画布审核与制作 | 交接本身不调用生成模型 |
| 正在分析 | 切换、新建、历史切换、报告交接按钮禁用；可点“停止”后切换 | 已开始的调用按网关规则计量 |

第一次进入另一个工作区可沿用当前模型，随后分别保留模型选择。技能选择按用户与工作区分桶，旧版技能偏好迁移到画布区；换账号时清理双方草稿、临时附件和当前对话，重新读取该账号的文字历史。对话只属于分析助手；画布入口隐藏分析消息，不删除分析消息。抽帧复制使用独立 Blob 地址，分析成功移除附件时不会使画布草稿里的原视频失效。

当前草稿、原文件和抽样图只在本次页面停留期间保留；离开页面或刷新后，可从分析历史恢复文字。跨页面草稿恢复、原视频与报告的长期关联还需要持久任务 / 素材库，不在这次切换更新中承诺。

## 2. 为什么造物能循环调用工具，原来的 XOi 主站主要是文本聊天

造物的 `src/components/agents/super/loop.ts` 会给模型提供 `tools`，接收 `tool_calls`，调用 `executeTool`，把结果作为 `role: tool` 消息回填，再请求模型，重复至完成或达到上限。`tools.ts` 提供生成图片、生成视频、TTS、网页获取、视频分析等实现。

原来的 XOi `backend/src/routes/aiAssistant/chat.ts` 只发 `messages + stream: true`，只转发 `delta.content`，没有注册工具，也没有执行与回填。主站首页还把发送按钮作为“进入画布”的入口，所以它承担文字规划和入口导航，而不是超级 Agent 执行器。

XOi 的剧本 / 生产模块已有部分 Agent 和工具实现，因此原因是**主站没有接执行链和权限分工**，不能据此认为整个 XOi 没有 Agent 或必须换模型。

本次分析链为：

```mermaid
flowchart LR
  U[分析助手：用户上传视频] --> F[浏览器抽取 12 帧]
  F --> V[后端验证本轮帧]
  V --> M[模型请求 analyze_video]
  M --> A[只允许视觉分析工具]
  A --> O[观察结果回填 tool 消息]
  O --> R[模型整理回复]
  R --> H[用户点击带入画布]
  H --> C[独立画布 Agent 制作]
```

这是限定一次工具执行的最小完整回传循环，不是造物 40 轮多工具的全部能力。只有视觉分析通过后才回填报告；未知工具、无效参数、半截工具调用、模型错误均停止执行。纯文本请求只调用一次聊天模型。

    references/  # 按原包保留，可能叫 refs
    scripts/
    assets/

市场数据库继续用于展示、分类、收藏、安装授权和版本索引。完整包由后端存储，封面可以作为公开静态资源；脚本和业务文件不能因为市场卡片需要就全部放进 public。

当前市场安装主要保存正文，主站单个正文最多读取 16000 字符，不能当作完整包加载。175 个包全部启用或塞进一个系统提示词也不合理：先按描述选技能，再按需读取正文与参考文件。

### 权限应怎么做

定义两个后端能力集合，而不是靠提示词保证分工：

- `analysis`：读已选 Skill 的允许文档、分析本轮授权素材、输出结构化方案；后续按需增加音轨分析 / 研究工具。
- `canvas`：只读写当前用户当前画布的允许节点、调用已授权媒体模型、把产物登记到该用户资产库。
- `worker`：由后端提交有类型的任务，持限定任务目录与输出权限。Skill 内容不能授予运行任意脚本、访问账号密钥或跨用户资产的权力。

有效工具 = Agent 能力白名单 ∩ 当前用户权限 ∩ 项目权限 ∩ 本轮素材权限 ∩ 当前模型支持。每个执行器再次验证，不接受前端说“已经授权”作为依据。用户网关身份和计费继承现有服务，不在前端保存新的平台密钥。

本次已在分析入口实施工具白名单、客户端历史角色过滤、输入图像验证和取消 / 超时。统一的用户 / 项目策略表、Worker 权限和全部画布工具适配还需后续实施。

## 5. 分阶段实施和验收

| 阶段 | 交付 | 验收标准 |
|---|---|---|
| 已做：分析入口 | 入口分工、抽帧、视觉工具回填、报告交接 | 浏览器真实抽帧；失败不报成功；分析端不能执行生成工具 |
| 下一步：Skill Registry | 导入 175 个完整包、描述索引、Skill 授权 / 版本、read_skill_file / asset | 175 包导入对账；每个有效引用可读取；越界 / 跨用户读取拒绝；正文不静默截断 |
| 随后：基础生成适配 | 图片生成 / 编辑、视频生成 / 查询、TTS，复用当前服务 | 选几个有参考资产的技能跑通真实产物、任务状态、计费和画布资产关联 |
| 再后：成片执行 | 持久队列、FFmpeg、BGM / 歌曲、字幕 / 音轨 | 多段成片能生成、失败恢复、取消任务、权限与账务可追溯 |
| 最后：专用技能 | 特效模型、手势 / 深度 / 口型、平台工作流替代 | 按分支记录“可用 / 部分可用 / 未支持”，有真实输入输出证据 |

首批不应承诺 175 个全部执行成功。建议先验收 6–10 个覆盖不同依赖的代表技能，打通共用工具，再扩大覆盖。Skill 卡片显示依赖和支持状态，缺工具时仍可使用其中的文字规划部分，但不能显示“已完整可用”。
