## 一、架构（部署形态）

```
用户浏览器
   │ HTTPS（Caddy/Nginx 反代，泛域名证书）
   ▼
┌───────────────────────────── 单机（首期） ─────────────────────────────┐
│  XOi 后端 (Node, 12121, 只绑 loopback)                                  │
│   ├─ 静态：/app/release（三前端产物 + 网关静态）                          │
│   ├─ 可变数据：/app/backend/data（OSS 素材 / 公告 / 草稿配置）            │
│   └─ 业务库 = 网关库（同一个 PostgreSQL，决策 D2）                        │
│  new-api 网关 (3000, 只绑 loopback) ── 上游渠道（各自 API Key 在服务器）  │
│  PostgreSQL 16（业务表 o_* + 网关表 users/logs/redemptions + mc_*）      │
└──────────────────────────────────────────────────────────────────────┘
```

- 端口只暴露 443（反代）；12121/3000/5432 全部 loopback 或 docker 内网。
- 发布用固定版本标签的镜像（`docker build` 三前端 + 后端），不走 `compose down -v`。
- 参考配置：`ops/nginx-single-node.conf.example`；进程守护 systemd 或 `docker compose up -d`（不含 `-v`）。

## 二、环境变量与密钥（服务器上注入，绝不进仓库）

| 变量 | 用途 | 要求 |
|---|---|---|
| `DATABASE_URL` / `NEWAPI_DATABASE_URL` | 业务库 + 网关库（同一条） | 强口令；备份策略见手册 |
| `NEWAPI_BASE_URL` | 网关地址 | 内网地址 |
| `NEWAPI_ADMIN_TOKEN` / 管理员账号 | 网关管理动作（加额度/建号/预算） | **只存在于服务器环境变量**（前端产物已验证无泄露） |
| `tokenKey`（o_setting 表） | XOi JWT 签名 | 部署时生成强随机值 |
| `XOI_ALLOW_PRIVATE_UPSTREAMS` | 出站私网白名单 | **生产必须不设/false** |
| `EDGE_AUTH_TOKEN` 等 | 域名签证书闸门等 | 随机强值 |

## 三、部署步骤（标准流程）

1. **构建**：`npm run build:all`（三前端）→ `backend npm run build`（后端产物）→ Docker 镜像打版本标签。
2. **门禁**（构建前自动/手动）：`node ops/check-console-routes.mjs --strict`（接口挂载比对）；`backend npm test`（含 announcements/budget 单测）。
3. **迁移**：后端启动自动建表（`ensureBudgetSchema`/`ensureAgentTables`/documents 等）；首次部署跑 `ops/release-preflight.mjs`。
4. **健康验收**（不能只看启动日志）：`/api/readyz` 200；登录 → 模型目录 → 建画布 → 生成一张图 → 积分明细有记录。
5. **回滚**：镜像回退旧版本标签；数据库用 `ops/backup-production.sh` 的备份点恢复（只允许回滚到"已备份且未营业"的窗口，禁止回滚已营业的积分账本）。

## 四、本轮测试结论（2026-10-24）

### 渗透测试（双账号实测，脚本化执行）

| 项 | 结果 |
|---|---|
| 账户隔离（画布/文件/文档/任务/计费 双账号交叉） | ✅ 全部 404/403，无泄露 |
| 管理接口越权（普通用户打 /api/admin/*） | ✅ 403 |
| **身份提升漏洞（严重·已修复）** | ❌→✅ `newApiSelfByAdmin` 原用 `/api/user/self`+模拟头，网关忽略模拟头恒返 root → **全部登录用户被判管理员**（生产同样存在）。已改用 `GET /api/user/:id` + 返回身份一致性校验；25 处调用方一并修复 |
| **卡密兑换资金归属（严重·已修复）** | ❌→✅ 实测用户兑换 ¥0.01 到账 root。已改为服务端直查网关库原子兑换（`FOR UPDATE` 行锁防重复）+ `add_quota` 记到登录用户 + 失败回滚核销；实测 B 兑换 5000 积分到本人、重复兑换被拒 |
| **积分明细数据归属（中·已修复）** | ❌→✅ 实测显示 root 的 348 条日志。已改直查网关库 `WHERE user_id` 本人数据 |
| SSRF（内网/云元数据/路径穿越） | ✅ 全部拦截（safeUrl 三层防护） |
| 限流 | ✅ 全局 1200/min、生成独立限流、download-output 30/min（实测 429） |
| 前端产物管理员令牌泄露 | ✅ 无 |

### 压力测试（本地单机，50 并发 × 200 请求/接口）

| 接口 | RPS | P95 | 结论 |
|---|---|---|---|
| 静态首页 / 公告 / 健康检查 | 3900–8300 | <35ms | ✅ |
| 画布列表 / 工作区 / reseller 身份 / 计费偏好 | 1500–1900 | <60ms | ✅ |
| 积分明细 | 546 | 165ms | ✅（修复后 0 错误） |
| 模型目录 | 95→缓存后单发 11ms | 并发 P95 仍 ~1s | 🟡 已加 15s 结果缓存（36 倍）；并发余下瓶颈 = **每请求 JWT 鉴权的 DB 查询**，部署时调大 PG 连接池（`knex pool.max`、`XOI_AGENT_DB_POOL_MAX`）即可摊平 |
| 工作区文档（混合压测出现 429） | — | — | ✅ 全局限流按预期生效，非故障 |

**压测结论**：单机 4 核/8G 量级可支撑数百并发在线；**2000 人目标**需要按手册做混合压测与连接池调参（部署文档遗留项）。

### 服务器规格怎么选（2核2G / 4核4G）

| 规格 | 能不能跑 | 配置 | 上限预期 |
|---|---|---|---|
| **2核2G** | ✅ 能跑，按低内存形态 | `ops/server-deploy/compose.2c2g.override.yml`（叠加在生产 compose 上）：PG shared_buffers 128MB/max_conn 40、new-api 320m、Node 512m 堆 + 700m 容器顶，三进程全部 mem_limit 硬顶；**磁盘至少 40G**（生成物存储增长） | 几十人同时在线、日活数百；生成走上游不吃本机 CPU，瓶颈在内存 |
| **4核4G** | ✅ 舒适区（推荐起步） | `compose.4c4g.override.yml`：PG shared_buffers 512MB/max_conn 80、Node 1G 堆、媒体 worker 6、并发 48 | 数百人同时在线、约 2000 注册量级；最终以手册 2000 人混合压测为准 |

**两条硬规矩（两种规格通用）**：
1. **构建绝不在服务器上做**——`npm ci + vite build` 峰值 1.5–2G，2G 机器必 OOM。镜像在本地/CI 构建推送到服务器（`docker pull` + `up -d`），版本更新 = 更新镜像标签；`XOI_UPDATE_MODE=git-script` 一键更新只在"服务器有构建余量"的机器上启用（4G 以上且磁盘充裕）。
2. **磁盘水位监控**：生成物存本机盘，视频按几十 MB/个增长——85% 告警；2G 内存机器的磁盘通常也小，建议定期把旧成品归档到对象存储或扩盘。

## 五、上线门槛（按顺序执行）

1. **代码层**（已完成）：两轮安全审计 + 渗透实测 + 三个资金/身份修复。
2. **人工渗透清单**：按《docs/渗透测试清单-2026-10-24.md》在**目标服务器**（生产配置）跑完全部勾选项——重点回归本轮三个修复。
3. **开收款前必修**（缺一不开）：
   - 网关合规条款确认 + 支付渠道配置（密钥只在服务器）；
   - **`/api/user/pay` 在线支付下单的归属核验**：与卡密同类的模拟头问题，必须在沙箱渠道实测"用户 A 下单 → 订单归属 A、回调加到 A"后才允许开在线支付（当前只有卡密模式不受影响）；
   - 新用户单日消费硬闸（当前只有提醒）——建议随开收款一并上。
4. **压测门槛**：目标服务器上按手册完成 2000 人混合压测（含生成任务），数据库连接池按压测结论调参。

## 六、上线后运维

- 备份：`ops/backup-production.sh` 定时跑（数据库 + /app/backend/data）。
- 监控最小集：`/api/readyz` 探活、`xoi_model_budgets` 活跃数、`xoi_media_queue` 积压、网关错误日志、单用户小时级消耗突增告警（SQL 示例见《在线支付开通与支付风控基线》第五节）。
- 应急：维护模式开关（console 运营设置，实时生效）；单用户异常 = 停用账号（管理后台用户管理页）。
