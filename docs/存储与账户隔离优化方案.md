## 0. 一句话结论

**账户隔离我们已经比造物强，不用抄；存储治理我们基本是空白，必须抄。**

造物的账户隔离本质是「每张表带 `user_id` + 文件 meta 记 `userId`」，但**读文件时完全不校验归属**——24 位十六进制 ID 就是凭据，知道链接就能看（`media-store.ts:346 resolveUpload` 不校验 user）。我们在 `canReadMedia` + `mediaGrant` 里做的是真归属校验 + HMAC 签名 URL，这一块**已经领先**，不要退回去学它。

反过来，造物有四层存储配额、TTL、引用感知的孤儿回收、磁盘水位熔断，这些我们**一条都没有**。多用户跑满磁盘那天，业务库和 new-api 会一起写不进去——造物 2026-10-04 就出过这个事故（见 `media-store.ts:270` 注释）。

## 1. 造物到底怎么存的

### 1.1 存储模型：三类 + 双文件

```
DATA_DIR/media/
  v-<taskId>.bin   .json   视频任务成品，TTL 1 天，过期可从上游重取
  i-<24hex>.bin    .json   出图，TTL 1 天，记录里留着上游 src 可按需回取
  u-<24hex>.bin    .json   用户上传，永久；没人引用 + 7 天没续期才删
```

- `.json` 侧车文件存 `{contentType, expiresAt, size, userId}`
- 写入一律 `.part` 临时文件 + `rename` 原子落盘（`media-store.ts:60,82,320`）
- 浏览器只拿到 `/api/media/<v|i|u>/<id>`，**上游域名不出现在任何响应里**

### 1.2 五层配额（这是最值得抄的部分）

| 层 | 规则 | 目的 |
|---|---|---|
| 请求频率 | 每用户每分钟 30 次上传 | 防脚本刷 |
| 字节速率 | 每用户每小时 2GB，**按实际写入字节记账** | 防 chunked 绕过 Content-Length |
| 单账号总量 | 附件合计 5GB | 防批量小号写满盘 |
| 单文件 | 上传 300MB / 回源 800MB | 防单请求打爆内存 |
| 磁盘水位 | 剩余 < 10GB 或 < 5% → 507 拒收（30 秒缓存） | **防全站 503** |

字节记账的细节值得单独抄：上传前按 `Content-Length` 预记一次，写完后用 `chargeUpload(actual - declared)` 补差额（`upload-quota.ts:56`）。只按声明的长度记，chunked 上传就记成 0，2GB/小时形同虚设。

### 1.3 成品转存（解决「存档断图」）

生成的图/视频 1 天就删，但用户会把地址存进作品、画布、PPT。造物的解法是 `retainAsUpload`：

- 成品 `v/i` → 复制成长期附件 `u`，ID = `sha256("retain:uid:kind:id").slice(0,24)`
- **幂等**：同一个人重复转存同一个成品，永远同一个号（网络重试不会存出好几份）
- 转存前校验归属：视频查 `tasks.user_id`，图片查 `mc_draw_logs.user_id`
- 转存后的 `u` 地址同样受「引用即保留」保护

### 1.4 引用感知回收

`media-retention.ts` 的做法：

1. 每轮扫描把「满 7 天没被续期」的 `u-*.json` 挑出来
2. **一次性**从各引用表（对话 / Skill / 作品 / 媒体项目 / 偏好）抽出所有被引用的附件号
3. 与目录做差集，差集里的删掉

关键设计：续期 = 改 meta 文件的 mtime（`fs.utimes`）。浏览器端项目（画布、会话只存在 localStorage）在打开/保存时调 `POST /api/media/touch` 来续期——**服务端看不见的引用，由客户端主动上报**。

### 1.5 安全细节

- MIME 白名单 + 魔数 sniff，**明确排除 `image/svg+xml` 和 `text/*`**。理由写在注释里：SVG 会被浏览器当文档渲染，在**主站 origin** 里执行脚本，能读到 localStorage 里的 JWT 和明文 `sk-`，`nosniff` 挡不住（因为声明的就是 SVG）
- 响应头强制 `CSP: default-src 'none'; sandbox`
- 非白名单类型强制 `content-disposition: attachment`
- 回源走 `safeMediaFetch`：逐跳校验、不连内网（防 SSRF）

## 3. 查出的具体问题

### P0-1 磁盘没有熔断，也没有回收

- 证据：`backend/src` 全量搜索无 `statfs` / `sweep` / `orphan`；`canvas-files.ts:60` 只有 `1GB` 上限且无删除接口
- 风险：多用户跑 3~6 个月，`data/oss` 只涨不跌。盘一满，`new-api` 的磁盘保护会让**每个** API 请求 503，不只是媒体
- 造物对应实现：`media-store.ts:277 diskLow()` + `sweep()`（10 分钟一轮）

### P0-2 生成物回源依赖上游账密

- 证据：`lib/workspace/imageRecover.ts` 用 `ZAOWU_LOGIN_USER/PASSWORD` 登录造物换 JWT，每次出图超时都走一次登录
- 风险：① 上游账号密码长期躺在我们 `.env`；② 每次超时登录一次，多并发下会撞 new-api 的会话上限（50），报 `Conflict`；③ 上游一旦改版，这条链路静默失效
- 现状说明：老链路（`generateAssets`/`batchGenerateAssetsImage`/`generateFlowImage`）**确实先落盘再返回站内 URL**，这块没问题；问题只在这条"迟到结果反查"的旁路

### P0-3 上传并发上限是 4，且单用户串行

- 证据：`canvas-files.ts:30-40`
- 风险：Web 多用户场景下，4 个并发就是全站天花板；同一用户开两个标签页上传，第二个直接 429「请等待当前上传完成」
- 附带：`express.raw({limit:"128mb"})` 全内存缓冲，4 并发峰值约 512MB

### P1-1 媒体鉴权每张图打一次库

- 证据：`privateMedia.ts:canReadMedia` 对 `/{projectId}/` 路径每次 `db('o_project').where({id})`
- 风险：一个项目页 50 张图 = 50 次 DB round-trip。叠加 `XOI_DB_POOL_MAX` 默认 **8**，池很快打满
- 附带：`o_project.userId` 是 `table.integer("userId")` **无索引**（`initDB.ts:126`），按用户查项目列表会全表扫

### P1-2 老上传口是 base64 JSON

- 证据：`assets/uploadClip.ts:45`、`assets/saveAssets.ts:29`、`production/editImage/uploadImage.ts:42`
- 风险：base64 膨胀 33%，25MB 上限实际只能传 ~18MB；解析后还要二次 Buffer 拷贝；这三个口**没有任何配额**

### P1-3 历史脏数据没有归属

- 证据：`data/oss/` 下存在 `1790988161967/`、`1792594206800/` 这种毫秒时间戳目录（int4 溢出遗留）
- 风险：`canReadMedia` 对这类路径只能放行 admin，普通用户永远访问不到，但文件永久占盘

### P2-1 媒体响应缺 CSP sandbox

- 造物在媒体响应上加 `CSP: default-src 'none'; sandbox`；我们只有全局 `nosniff`
- 当前扩展名白名单已排除 svg/html，风险低，属纵深防御

### P2-2 无存储用量表

- 无法回答「这个用户占了多少」「哪个项目最占盘」「该不该限他」

## 4. 优化方案

### 阶段一：止血（1~2 天，可独立上线）

**目标：盘满不再拖垮全站；用户能自己删文件。**

1. **磁盘水位熔断** — 新增 `utils/storageGuard.ts`
   - `diskLow()`：`fs.statfs(ossDir)`，剩余 < `max(10GB, 5%)` 即熔断，30 秒缓存
   - 接到所有写入口（canvas-files / uploadClip / saveAssets / uploadImage / one-stop 落盘），返回 `507`
   - 失败时**不**熔断（监控出错不能拒掉正常上传，同造物 `media-store.ts:285` 的取舍）

2. **画布文件删除接口** — `routes/canvas-files.ts` 补 `DELETE /:name`
   - 校验文件名正则 `^[a-f0-9]{32}\.(png|jpg|...)$`，且必须落在 `FILES_DIR/{req.user.id}/` 内
   - `realpath` 比对防符号链接（复用 `outputArchive.ts:resolveOutputAsset` 的写法）
   - 前端画布素材面板补删除按钮

3. **生成物旁路去掉账密登录**
   - `imageRecover` 改为：优先读本地 `xoi_draw_logs`；上游反查降级为「用服务端长期令牌」而非账密，且加 60 秒熔断（失败一次就停一分钟），避免并发登录撞会话上限

### 阶段二：配额与计量（3~5 天，核心）

**目标：把造物的四层配额落到 DB，而不是扫目录。**

新增表（`initDB.ts`）：

```sql
CREATE TABLE xoi_storage_usage (
  user_id      bigint PRIMARY KEY,
  bytes        bigint  NOT NULL DEFAULT 0,   -- 当前占用
  file_count   integer NOT NULL DEFAULT 0,
  quota_bytes  bigint  NOT NULL DEFAULT 1073741824,  -- 默认 1GB，可按用户/套餐调
  updated_at   bigint  NOT NULL
);

CREATE TABLE xoi_storage_rate (
  user_id   bigint NOT NULL,
  window_at bigint NOT NULL,      -- 分钟/小时桶
  bytes     bigint NOT NULL DEFAULT 0,
  hits      integer NOT NULL DEFAULT 0,
  PRIMARY KEY (user_id, window_at)
);
```

- 记账：写完文件后 `UPDATE ... SET bytes = bytes + ? WHERE user_id = ?`（单语句原子，不要读改写）
- 限额检查：`SELECT bytes, quota_bytes FROM xoi_storage_usage WHERE user_id = ? FOR UPDATE`
- 速率检查：按分钟桶 `INSERT ... ON CONFLICT DO UPDATE SET bytes = bytes + EXCLUDED.bytes, hits = hits + 1`
- **为什么不用造物那套扫目录**：它自己就承认 10 分钟缓存是为了掩盖 O(n)（`media-store.ts:291`）。我们直接进 DB，索引查询 O(1)，且多副本天然一致

配套：

4. **canvas-files 用用量表替代 readdir+stat**（删掉 `canvas-files.ts:58-61` 的扫描）
5. **老上传口接配额**（`uploadClip` / `saveAssets` / `uploadImage`）
6. **上传改流式**：canvas-files 的 `express.raw` 换成 `stream.pipeline` 直落盘 + 边写边计字节，峰值内存从 128MB 降到几十 KB

### 阶段三：生命周期（3~5 天）

**目标：文件有出生也有死亡。**

7. **孤儿回收任务**（新增 `lib/workspace/storageSweep.ts`）
   - 每 6 小时一轮，只扫「`updated_at` 早于 7 天」的候选
   - 引用反查**用 `NOT EXISTS` 逐表判断**，不要把文档抽出来跑正则（造物 `media-retention.ts:referencedIdsQuery` 会把所有文档 text 拼起来跑一次正则，文档大了直接爆内存）
   - 覆盖引用表：`o_image.filePath`、`o_video.filePath`、`o_assets.imageId`、`xoi_canvas_documents`、`xoi_draw_logs`、`o_project` 封面
   - **查库出错就整轮不删**（宁可少删，不能误删）
8. **TTL 分层**
   - 生成物（未转存）保留 30 天 → 到期删
   - 用户上传（被引用）永久
   - 缩略图跟原图同生命周期
9. **历史脏数据处理**：`1790988161967/` 这类无归属目录，先移到 `data/oss/_orphan/` 观察 30 天再删

### 阶段四：并发与可观测（2~3 天）

10. **上传背压重做**
    - 删掉全局 `uploadsInFlight >= 4`，改成按用户令牌桶（复用 `sharedRateLimiter`：每用户 60 秒 30 次）
    - 全局并发放到 32（可配 `XOI_UPLOAD_GLOBAL_CONCURRENCY`）
    - 同用户允许 2~4 个并发（多标签页正常使用），不要串行
11. **媒体鉴权加缓存** — `canReadMedia` 的项目归属查询加 60 秒 LRU（key = `projectId`）
    - 失效时机：项目删除/转让时主动清（`creativeDeletion` 里已有事务钩子）
    - 收益：50 张图从 50 次查询降到 1 次
12. **`o_project.userId` 补索引** + `XOI_DB_POOL_MAX` 至少 `CPU核数 × 2`（当前默认 8 偏低）
13. **存储用量仪表**：控制台加「我的空间」页（已用/配额/文件数/清理入口），管理端加容量总览

## 5. 落地顺序与验收

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| 一 | 磁盘熔断 + 删除接口 + 旁路去账密 | 手动把剩余空间模拟到 1GB，上传返回 507 且业务 API 仍 200；用户能删文件并立刻释放配额 |
| 二 | 用量表 + 四层配额 + 流式上传 | 单账号超 1GB 被拒；chunked 上传无法绕过字节限额；128MB 上传进程 RSS 增量 < 50MB |
| 三 | 孤儿回收 + TTL | 造 100 个无引用文件，7 天后（可把阈值调到 1 分钟验证）全部清掉；被项目引用的一个都不少 |
| 四 | 背压 + 缓存 + 索引 | 20 并发上传全成功且 P99 < 3s；项目页 50 图首屏 DB 查询数 ≤ 2；池等待时间为 0 |

**不建议动的部分**：`canReadMedia` / `mediaGrant` / `resourceScope` / `creativeDeletion` / `mediaQueue`。这些是我们比造物做得好的地方，改造只会引入回归。

## 6. 一句话取舍说明

造物这套是「单实例 + 文件系统即数据库」的写法，简单但两处会绊倒多副本：配额在进程内存里、用量靠扫目录。我们照抄**规则**（四层限额、TTL、引用回收、原子写、魔数校验），但**载体换成 PG**——理由和我们当初把业务库并进 new-api 的库一样：能进事务、能多副本、能查询聚合。

| 上游返回 429 | 无熔断，每个新请求继续打，用户持续看到「分组负载已饱和」 | 连续 5 次后熔断 30 秒，期间**不提交上游、不计费**，直接提示稍后重试 |
| 几十个请求排队 | 每 600–1200ms 抢一次 advisory lock，每秒上百次锁争用 | 无锁只读检查，满了不进事务；退避指数化，90 秒内最多约 30 次 |

## 8. 第二轮执行记录（企业级收口）

### 8.1 配额改分域模型

一张表 `xoi_storage_usage(user_id, scope, bytes, file_count, quota_bytes, updated_at)`，复合主键 `(user_id, scope)`。

| 域 | 内容 | 配额 |
|---|---|---|
| `canvas` | 用户自己传的画布素材 | **1GB 硬配额**，有删除出口 |
| `project` | 项目里的生成物与素材 | 只记账，不限额 |
| `onestop` | 一站式合成的成片 | 只记账，不限额 |

为什么不设一个总量：生成物数量由「生成了多少」决定，对它限额会让用户不敢生成，而生成本来已按次计费。**只对用户能自己清理的那部分设配额**，配额才有意义 —— 满了让他删就能恢复。总量由 `storageGuard` 的磁盘水位兜底。

### 8.2 老上传口统一收口

新增 `utils/mediaWrite.ts`：`解码 → 大小上限 → 魔数校验 → 磁盘水位 → 记账 → 原子落盘`，失败回滚配额。

接入四个之前「裸写」的入口：

| 接口 | 原来的问题 | 现在 |
|---|---|---|
| `assets/uploadClip` | base64 直接写盘，不校验文件头、不限大小、不记账 | `autoDetect` 以文件头定类型 |
| `assets/saveAssets` | **固定存成 .png**，客户端传 jpg 也写成 png，扩展名与内容对不上 | 按实际类型落盘 |
| `assets/addAudioAssets` | 按 mime 猜扩展名，无校验 | 补齐 aiff / flac / m4a 魔数 |
| `production/editImage/uploadImage` | `match(...)[1]` 取不到会抛 TypeError | 统一解码，错误可控 |

`mediaSecurity.isAllowedMedia` 补了 `m4a`（ISOBMFF，与 mp4 同头）、`flac`（`fLaC`）、`aiff`（`FORM`+`AIFF`）。

### 8.3 孤儿回收：`lib/workspace/storageSweep.ts`

与造物的关键差异：造物把**所有引用表的文档 text 拼起来跑一次全局正则**再和目录做差集，文档多了就是全表顺序扫描 + 巨型字符串，且每轮重算全部历史引用。这里反过来 —— **先有候选，再判引用**：

1. 扫 `canvas-files/*/` 里 mtime 超过 TTL 的文件（每轮上限 500 个）
2. 只用这批候选文件名去各表做 `LIKE ANY(ARRAY[...])`，每表一轮扫一次
3. 返回的行在 Node 侧提名字，与候选做差集

引用表：`xoi_canvas_documents` / `xoi_workspace_documents` / `xoi_generation_tasks` / `o_image` / `o_video` / `o_storyboard`。表或列不存在自动跳过。

**安全阀（四条，缺一不可）**
- 默认 **dry-run**：只报告不删，必须 `XOI_STORAGE_SWEEP_DELETE=1` 才真删
- 任意一张引用表查询失败 → **整轮一个都不删**（宁可少删，不能误删）
- 删之前再 stat 一次 mtime：扫库期间刚被 touch 的跳过
- **跨实例互斥**：`pg_try_advisory_lock` 显式借一条连接持有到本轮结束（advisory lock 是会话级的，knex 池里 lock/unlock 落不同连接会静默失效），多副本部署时只有一个实例真正扫描删除

配套 `POST /api/canvas-files/touch`：画布打开/保存时把素材 mtime 刷新，回收从这一刻重新计时。只接受 `/canvas-files/{自己的uid}/` 前缀或纯文件名。

### 8.4 鉴权缓存与索引

- `canReadMedia` 的项目归属查询加 **60 秒 LRU**（上限 5000 条）。一个项目页 50 张图 = 50 次 DB 往返，原来全打在连接池上
- admin 读项目素材跳过归属查询（文件不存在自然 404）
- `o_project.userId` 补索引 `o_project_user_idx`（`fixDB.ts`，`CREATE INDEX IF NOT EXISTS` 幂等）
- `XOI_DB_POOL_MAX` 默认值从固定 8 改为 `min(32, max(8, CPU×2))` —— 媒体鉴权、生成队列、业务查询、计费共用一条池

### 8.5 管理端监控

`GET /api/admin/storage/overview`：磁盘水位、分域容量、Top10 用户、队列各状态计数、活跃模型租约、已熔断的上游。
`POST /api/admin/storage/sweep`：手动跑一轮（仍受 dry-run 开关约束）。
`GET /api/admin/storage/users/:id`：单账号按域拆开的用量。
`POST /api/admin/storage/quota`：调某人 canvas 配额（0 = 禁止再上传）。

### 8.6 顺手修掉的并发隐患

`lib/workspace/imageRecover.ts` 原来**每次反查都 `POST /api/user/login`**。高峰期几十个任务同时超时就是几十次登录，new-api 有并发会话上限（50），超了回 Conflict，反查全废。
现在按 13 分钟缓存 JWT（上游有效期 15 分钟，留 2 分钟余量），并用同一个 in-flight promise 合并并发登录。
