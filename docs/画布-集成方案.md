## 一、现状架构（为什么现在是「单独跑」）

```
本机绝对路径（仓库外!）
/Users/zhaochenyu/Desktop/C_code/infinite-canvas-main/web   ← Next.js 项目，192 个 TS/TSX，2.8MB 源码
        ▲
        │  vite resolveId 插件：@/ → 上游 src；next/navigation、next/dynamic → 本地 shim
        │
frontend/atelier（Vite + React19 薄壳）                      ← 独立 npm install / build
        ▼  构建产物
frontend/public/atelier-canvas/                             ← cp 进后端静态目录
        ▼
backend/data/web/atelier-canvas/                            ← express 托管
        ▲
        │  <iframe src="/atelier-canvas/?source=xoi&...">
        │  桥接：upstream-canvas-bridge.tsx（4 条链路 + sessionStorage/localStorage 握手）
        │
frontend/src/views/canvas/index.vue（Vue 主站，hash 路由）
```

**为什么要单独跑（三个硬理由）**：

1. **框架不同**：主站 Vue3 + hash 路由；画布是 React 19 + Next.js 范式。Vue 无法直接 import React 组件树。
2. **画布太重**：React 全家桶 + zustand + ai-sdk + 图片处理 + antd/radix，独立 bundle 现在就有数 MB；塞进主站会把 Vue 产物撑爆，还得做样式/依赖隔离。
3. **上游是活的**：画布逻辑要改**上游仓**（配置弹窗 XOi 化就是直接改的上游文件），上游还在演进，隔离构建让上游升级保持低成本。

**造物为什么没有这个问题**：造物（zaowu-engine-main）本身就是 **Next.js 单体应用**，画布是同一个 Next 应用里的 `/canvas` 路由——同仓、同框架、同进程、同构建，天然不存在「单独跑」。infinite-canvas-main 就是从这类单体里抽出来的画布部分。XOi 主站是 Vue，**照搬造物的前提（同框架）不成立**，只能找等价物。

## 三、方案 B：收编进仓（推荐，立刻做）

**做什么**：把上游画布源码变成仓库的一部分，删掉对绝对路径的依赖。**运行形态不变**（仍是独立构建 + iframe，桥接/两套 store 全都不动）。

**步骤**：

1. `git subtree add` 或直接拷贝：`infinite-canvas-main/web/src` → `frontend/atelier/upstream/src`（约 2.8MB 源码；`node_modules`/`bun.lock`/`next.config.ts` 不要，构建由薄壳负责）
2. `atelier/vite.config.ts`：`upstreamWebDir` 从绝对路径改为 `resolve(webDir, "upstream")`；resolveId 插件逻辑原样保留（shim 重定向继续生效）
3. 上游里被我们直接改过的文件（如 `app-config-modal.tsx` 的 XOi 化）以仓内版本为准，之后**画布改动一律改仓内文件**，上游仓降级为「只读参考」
4. `tsconfig.json` include 加上 `upstream`；typecheck 跑通
5. 回归：四条链路（发图导入 / 新建画布 / 提示词交接 / 广场复刻）+ 配置弹窗 + 生成出图

**收益**：仓库自包含、换机器/CI 可构建、画布改动有 git 历史可回溯；上游仓仍可对照升级（diff 搬运）。

**代价**：上游升级从「git pull」变成「diff 手动搬」——可接受，画布的 XOi 化改造本来就已经和上游分叉了。

## 四、方案 C：同仓双入口（长期可选）

把 React 画布变成主站 Vite 构建的**第二个入口**，同一产物、同源服务，去掉 iframe：

- **构建**：`frontend/vite.config.ts` 配 `rollupOptions.input` 双入口（Vue 主站 + React 画布）；React 相关依赖做 `manualChunks` 隔离，避免污染主站 bundle
- **路由**：主站 hash 路由保留；`/#/canvas` 时挂载 React 入口（或改为 history 多页：`/canvas` 路径由后端直接 serve React HTML，与 `/console` 同模式——**backend 已有先例**，console 就是这么挂的）
- **移植成本**：Next 范式 → 纯 Vite（next/dynamic、next/navigation、App Router 假设）已在薄壳里解决过一遍，搬运 shim 即可；两套 store 合并成一套（现在 atelier store 只写不读的尴尬局面自然消失）
- **收益**：去掉 iframe 桥接四条链路、单产物部署、登录态/接口同源直连
- **风险**：双框架共存的心智负担、React 19 与 Vite 插件链的版本协调、回归面大

**触发条件**：什么时候值得做？当「iframe 桥接的新链路维护成本」或「双产物部署」再烦到你 2~3 次的时候。方案 B 做完后 C 的迁移对象变成仓内目录，成本更低，两者不冲突。

---

## 五、不推荐

- **D 微前端**（qiankun/wujie）：为单一子应用引入整套微前端运行时，双框架 + 单场景，收益配不上复杂度。
- **主站迁 Next/React**：等于重写主站，不在讨论范围。
