# 管理员发布中心与平滑更新

## 结论与当前边界

服务器更新不应采用“停止全部服务、覆盖目录、重新启动”。目标是新旧两套应用短时并行，验证新版后切流，旧版完成在途任务后再退出。数据库、NewAPI 和媒体存储独立保留，不随每次 XOi 页面更新重启。

本轮实现管理员发布中心和节点排空基础，**未部署生产蓝绿拓扑、未执行生产切流，也未验收2000人同时在线**。现有 Compose 仍是单节点模板，不要直接 scale 或把开关设1就认为已具备高可用。

## NewAPI 哪些可以直接复用

以本工作区实际接入为准：

- 账号与权限来自 NewAPI；普通用户、平台管理员与超级管理员沿用现有体系，不再创建独立运维账号表。
- 渠道、模型计费、额度与消费日志继续由已有网关接入负责。发布中心不更改这些数据，不接收管理员 Key，也不向浏览器返回服务端凭据。
- XOi 应用镜像、数据库变更兼容性、画布和长任务排空不是当前 NewAPI 适配层的职责，需要 XOi 发布机制和服务器部署工具配合。不能把模型渠道管理当成整站发布系统。

代码依据：`loadAuthUser.ts` 每次读取网关 users 权限；`reseller.ts` 的 `/me` 已按 role>=100 标识root。本轮发布操作使用同样的超级管理员门槛，并在变更事务中再次核验权限。

## 管理员入口与隔离

管理控制台新增“发布中心”，地址 `/console/reseller/admin/releases`。仅 NewAPI role>=100、账号正常且未删除的超级管理员可访问。

- 普通平台管理员(role10)、代理、团队成员、普通用户不能读取节点或下发指令。
- 侧栏和快捷搜索按身份隐藏入口；真正安全边界是后端验证，不是路由名字隐蔽。
- 现有JWT只用于确定用户ID，不信任其中自称admin/root的字段。降权后原凭据也不再具有运维权限。
- 读操作返回最小节点信息：版本标签、节点标识、心跳、活动计数和最近50条控制审计；不返回路径、环境变量、数据库地址、模型密钥或原始任务内容。
- 变更需要节点状态版本、明确动作、确认标记、自定义意图头和操作原因；每次记录操作人、节点、动作、版本与时间。冲突/网络失败不自动重试，先刷新核对。
- 恢复接流也会在后端核验依赖就绪，不能绕过页面上的禁用按钮激活一个不健康节点。
- 不提供任意shell、远程脚本URL、Docker socket、在线上传可执行代码或“万能重启”接口。真正安装镜像、Nginx切流和回滚由SSH/受控CI账号执行，建议MFA与私网/VPN入口。

接口为 `GET /api/admin/releases` 和 `POST /api/admin/releases/:id/control`，只接受drain/resume，不是容器管理API。

## 默认安全配置

```dotenv
XOI_CANVAS_STORAGE=postgres
XOI_RELEASE_ROLLOUT_ENABLED=0
XOI_INSTANCE_LABEL=xoi-blue
XOI_RELEASE_START_MODE=active
XOI_RELEASE_CLUSTER=xoi-prod
```

旧服务器必须先按画布迁移手册完成导入，不能直接从files改postgres。发布摘流开关默认关闭；打开之前必须确认共享媒体、负载均衡、会话策略、预算和队列跨实例约束，完成预发演练。

蓝绿节点的 `XOI_RELEASE_CLUSTER` 必须相同；不同部署、租户或测试/生产环境必须不同。节点、操作记录与备用节点检查均按部署组隔离。生产启用摘流而未设置部署组时拒绝启动，不能仅因连接同一网关数据库就把其它业务当成备用节点。

候选节点可以设 `XOI_RELEASE_START_MODE=standby`：启动时拒绝业务请求、不领取新媒体任务，但可通过有权限的发布中心读取依赖就绪状态。核验后由超级管理员恢复接流。standby/draining 的 `/api/readyz` 返回503是刻意行为，不代表需要自动重启；`/api/healthz` 仍用于存活检查。不要把readyz失败当作自动重启理由。

## 一次应用版本更新如何执行

1. **构建，不在线改代码。** CI构建带明确 `XOI_RELEASE_ID` 的固定镜像/摘要，执行类型、单元、权限、数据库兼容和只读预检查；前端文件使用内容哈希。记录上一版可用镜像。
2. **只做兼容迁移。** 先新增表/字段，保证旧版仍可运行；删除或重命名旧字段放在后续独立发布，不能一边运行旧版一边破坏其数据结构。对账与备份检查点应按已有手册执行。
3. **启动候选节点。** 使用独立容器和内部端口，不抢占旧节点端口，不把两套程序写进同一可变目录。新旧程序共用已验收的PG、媒体对象存储/共享媒体与稳定密钥。候选先用standby，超级管理员在发布中心核对版本、依赖和状态。
4. **启用并验证新版。** 恢复候选接流，确认readyz通过；从候选的私网地址执行 `ops/release-preflight.mjs --base <candidate-origin> --expected-release <release-id>`。这一步先不开放真实模型测试。运维在反向代理配置检查通过后做平滑reload，让新连接只去新版；保留旧连接到旧版完成任务。
5. **排空旧节点。** 只有在有健康替代节点、postgres画布模式且显式启用摘流后才能申请。全局事务锁防止两个管理员同时摘掉最后两个节点。旧节点拒绝新业务请求和新Socket chat，不再领取媒体任务；已接受的HTTP、Socket逻辑任务及媒体任务继续完成，媒体租约持续续期。
6. **核对后退出旧版。** 等心跳确认draining、已跟踪任务归零，并核对上游任务、账单、旧任务和长连接后，再由部署工具停止旧容器。不要一看到“申请成功”就立即kill。进程SIGTERM的45秒等待只是兜底，不是400秒视频任务的完成保证。
7. **观察与回滚。** 观察错误率、接口耗时、队列、预算和扣费回执。新版异常先将代理流量切回兼容的旧应用镜像，不重放不确定任务；不要把已产生新交易的数据库恢复到旧快照继续营业。

管理员的控制指令最多约一个心跳周期后被节点观察到。必须等“观察到排空”再判断，不把数据库已登记当作节点已经停止接任务。

## 页面、API和长连接的注意点

- 只改前端时可发布静态资源，不必重启API。资源先上传、入口最后切换，保留旧哈希文件，让已打开页面仍能加载旧资源。
- 本地新增 `node frontend/scripts/sync-backend-web.mjs --console-only`，只更新管理页面，不覆盖主站/画布或公告；这是本地发布工具，不是生产蓝绿控制器。
- 新旧后端并行时，静态资源应由独立静态入口/CDN或兼容资源集提供，避免新版HTML请求的哈希文件落到只有旧资源的实例。不要简单轮询两个互不包含对方资源的静态目录。
- 不自动重试生成、支付或管理变更POST；请求结果不确定时先查任务/账单/操作记录，否则可能重复提交。安全GET可由明确配置的客户端重试。
- 已建立的Socket连接不能靠Nginx reload搬家。当前先等待其中的逻辑任务完成，再断开退出；自动迁移会话/全量重连恢复尚未验收，不承诺所有页面完全无感。
- 支付回调在排空期间仍允许进入并结算，沿用原验签和幂等，不因应用更新丢弃回调。

## 剩余上线门槛

1. 真实预发双节点、负载均衡切流与回滚演练，不能只依赖节点心跳判断外部入口健康。
2. 共享媒体/对象存储、上传续传与下载Range；程序与用户数据隔离。
3. API与Worker进一步拆分；旧版任务执行期间的代码/数据契约兼容，非媒体旧后台任务与Socket恢复的完整覆盖。
4. 新旧版本静态资源兼容、数据库完整备份恢复演练、镜像内容/密钥与第三方许可核对。
5. 2000真实身份混合压测与上游并发容量验收。不能把节点排空或合成探针测试当作容量证明。

当前发布中心只用于受控观测和摘流，不会替操作员绕过这些门槛。

## GitHub 地址更新如何接入（方案，尚未启用自动安装）

可以把 GitHub 作为发布源，但不是在网站里输入任意URL就执行git pull或远程安装脚本。当前工作区有GitHub远程配置，未发现 `.github/workflows` 发布流水线，尚未绑定经过确认的XOi更新仓库或自动安装流程。

建议下一阶段分开实现：

1. 超级管理员预先绑定自己的XOi仓库白名单，不能误用原项目仓库覆盖定制版；选择明确的Release/tag并锁定commit，不无提示地跟随变化中的分支。
2. 只读检查版本、变更说明、数据库兼容声明与构建结果。私有仓库凭据仅保存在服务器/CI密钥存储，最小只读权限，不提交到代码、不返回浏览器。
3. CI生成固定版本镜像或发布包，记录摘要并验签；构建/检查失败时不得进入安装环节。不要将不可信链接下载的源码直接放进现网执行。
4. 预发验证后，由超级管理员明确批准；受限部署代理启动候选节点，按本手册切流和排空。Web进程不拥有任意shell或Docker socket。
5. 保留上一版兼容应用与旧静态文件；回滚切应用和入口，不倒退已产生新交易的账本。

实际接入前仍需用户确认：自己的XOi仓库地址、版本发布规则、私有仓库授权方式，以及目标服务器/镜像仓库配置。本轮未登录GitHub、未pull、未push、未创建Release或开启自动安装。
