# XOi 服务器部署与 2000 并发评估

评估日期：2026-10-11。依据本仓库实际代码、Docker 配置与官方文档。**以下服务器规格是用于采购和压测的规划估计，没有完成 2000 并发验证；不是容量承诺。**本次交付包含只读 API 压测脚本和单节点 Nginx 参考配置，没有连接生产服务器、购买资源或调用收费模型。

## 1. 能否支持 2000 人同时使用

可以作为明确的扩展目标，但需要区分两种需求：

- **2000 人同时在线**：浏览页面、编辑项目、间歇发起生成。通过静态资源优化、数据库查询优化、文件存储改造和任务队列，具有实现条件。应以真实工作负载压测确认。
- **2000 个 AI 任务同时运行**：服务器能接收请求，不代表供应商能同时生成。真正限制通常是模型供应商并发额度、RPM/TPM、网关吞吐、长连接、媒体搬运和资金预算。需要上游合同/配额确认、持久任务与全局限流。不能通过单纯增加 CPU 承诺实现。

**当前代码不宜直接复制多个应用实例上线。**进程内任务、文件画布、缓存和定时器尚未完成跨实例协调。先做稳定单实例上线与压测，再逐项消除这些阻塞点。服务器只转发云模型时通常不需要 GPU；如果决定自托管模型，必须按具体模型、精度、上下文和生成速率另做 GPU 容量测算。

## 2. 当前真实架构与瓶颈

| 代码/配置依据 | 实际情况 | 对上线/扩展的影响 |
| --- | --- | --- |
| `backend/src/utils/db.ts`、`docker-compose.yml` | 业务表与 NewAPI 的 users/tokens/logs 等位于同一个 PostgreSQL 数据库；跨表事务与收益聚合依赖同库 | 不能照旧文档重新建一个独立业务库或当成 SQLite。网关与业务会竞争数据库连接、IO、锁和日志空间 |
| `backend/src/lib/agent/db.ts` | 代理/团队/市场体系另外维护 pg 池，最大 8；`utils/newapi.ts` 另有按需初始化的 pg 池 | 总连接数不能只算业务 Knex 池；实例增加会放大总连接需求 |
| `backend/src/routes/login/login.ts` | 向 NewAPI 校验凭据，再同步本地用户镜像、签 JWT | 登录延迟包含网关与共享 PG，必须拆分观测各段，而不是只调前端 loading |
| `backend/src/utils/quota.ts`、`routes/login/self.ts` | 本次优化已让余额直读复用业务 PG 池，支持两个连接变量；self 仍要求 fresh 读取 | 修复原先只认 NEWAPI_PG_URL 导致回源网关的问题；保留实时余额语义。没有增加第二本扣费账本 |
| `backend/src/routes/project/getProject.ts` | 项目列表 SELECT 后并行做 6 个进度聚合；没有列表分页 | 不是逐项目 N+1，但大用户列表和多个同时请求会占满池；需要分页、预聚合、按查询计划检查索引 |
| `backend/src/routes/canvas.ts` | 每次列画布同步扫描目录并解析全部 JSON，再按用户过滤；保存也使用同步文件 IO | 数据量增大时会阻塞 Node 事件循环。直接加 CPU 核数不能解决单进程主线程阻塞 |
| `backend/src/routes/canvas-compat.ts` | 文件读取/原子改名与本地目录，同样存在同步操作 | 原子改名防半截文件不等于跨进程读改写事务；共享盘也不能自动防止丢更新 |
| `backend/src/utils/ownedTasks.ts`、`routes/canvas-stubs.ts` | 图片、视频任务各用一个进程内 Map；每个 Map 最多 2000 条记录，单用户各最多 6 个 running；非 running 记录保留约 24 小时并按需清理 | 重启会失去本地状态；轮询到另一实例找不到任务。**2000 是任务记录上限，不是已支持 2000 用户/生成并发的证据** |
| `backend/src/routes/assetsGenerate/*`、`production/workbench/batchGeneratePrompt.ts` | `p-limit` 控制单次批量请求的并发 | 多用户请求可以叠加，不能代替平台级/模型级全局并发限制 |
| `backend/src/socket/index.ts`、`app.ts` | Socket.IO 单进程；未接共享 adapter；连接计数/事件限频在本地 Map；每次连接需要身份与项目权限查询 | 横向扩容需考虑 Socket.IO 会话路由、跨节点事件、统一计数；不能直接 PM2 cluster |
| `backend/src/lib/captchaService.ts`、`failCounter.ts`、`middleware/rateLimiter.ts` | 验证码答案、失败计数与 HTTP 限流在进程内 | 不同实例会出现验证码不存在、风控/限流额度叠加；需共享 Redis/一致存储 |
| `backend/src/lib/reseller/store.ts` | JSON 文件 + 本地无限期缓存 + 每 key 进程内写入链 | 多进程缓存失效与读改写覆盖问题；建议迁 PG 并使用事务/版本号，不能仅改成共享卷 |
| `backend/src/lib/team/store.ts` | 团队定时任务已有 PG advisory lock | 保留现有锁保护；但每实例仍启动 timer，不代表整个系统定时任务都已协调 |
| `backend/src/lib/agent/store.ts`、`lib/model-catalog/sync.ts` | 代理补扫每 10 分钟、价格同步每 15 分钟；价格同步仅进程内 running 防重入 | 多节点会重复执行/竞争；迁独立 scheduler 或加入跨实例锁，并测幂等 |
| `backend/src/utils/oss.ts`、`routes/canvas-files.ts` | 实际媒体写在本地 `data/oss`；设置 ossURL 只改变访问前缀 | CDN/对象存储不是改环境变量即可完成。要改上传、下载、权限、缩略图、迁移和签名URL |
| `backend/src/app.ts` | Express 同时服务静态页面、API、媒体与缩略图；JSON 默认 25 MB | 大请求、base64、全量 Buffer 和图片处理会与业务抢内存/CPU，需分流和限制大小 |
| `docker-entrypoint.sh` | 每次启动刷新 data 下程序资产并递归 chown | 媒体卷很大时启动变慢。多实例共用整个 data 卷会互相刷新代码；需拆分不可变镜像资产与用户数据 |
| `backend/src/app.ts` | healthz 只表示存活，readyz 验证 PG 与 NewAPI | LB 应使用 readyz；健康检查不能证明模型供应商可用 |

本次新增连接池参数：`XOI_DB_POOL_MAX` 默认 8，`XOI_DB_ACQUIRE_TIMEOUT_MS` 默认 10000 毫秒。先记录连接池等待再调整；**不建议因为目标是 2000 人就把连接池直接改到 2000**。所有实例、NewAPI、后台工具、迁移与监控都要预留预算。估算公式是 `应用副本数 × 每副本所有池max之和 + NewAPI全部池 + worker池 + 运维保留 < PG max_connections`；不是一个池的8条连接乘完就结束。[node-postgres 池容量官方说明](https://node-postgres.com/guides/pool-sizing)

## 3. 采购和容量规划起点

假设模型由外部 API 提供，2000 在线用户中大部分是浏览/编辑，约每 10 秒产生一次小型 API 请求，媒体走对象存储/CDN。供应商、地区、峰值活动比例、媒体大小、项目规模和 API 配额尚未确定。

| 阶段 | 应用/API 与 NewAPI | 数据库 | 缓存/任务/媒体 | 适用条件 |
| --- | --- | --- | --- | --- |
| 小规模试运营 | 1 台 8 vCPU / 16 GB，API 与 NewAPI 可暂同主机、分别容器；不用 cluster | 推荐单独 4 vCPU / 16 GB、200–500 GB SSD，业务与网关同一个库 | 本地媒体盘另留 500 GB 起，做异机备份；尚未接 Redis 时只跑单应用实例 | 从 50/100/200 用户逐级测，不承诺当前单实例扛住 2000 |
| 有条件的低预算合并部署 | 1 台 8 vCPU / 32 GB / 1 TB SSD，应用、网关、PG 共机 | 同机 PG | 远端备份必需 | 仅用于试运营/压测；单点故障、构建OOM、媒体挤盘风险更高 |
| 2000 同时在线目标架构 | API 2 台 × 8 vCPU / 16 GB；网关 2 台 × 4 vCPU / 8 GB，前置LB | 8 vCPU / 32 GB 起、500 GB–1 TB SSD、约 3000+ 基线 IOPS 的托管 PG；按实测升级，高可用备节点另计 | Redis 2–4 vCPU / 4–8 GB + HA；worker 先 2 台 × 4–8 vCPU / 8–16 GB；对象存储/CDN | **完成第 5 节改造后**才可使用这些副本；网关副本也需确认所部署 NewAPI 版本的共享会话/缓存/计费支持 |

这些规格包括可用余量，但不是官方最低配置。资源买得更大也不会自动消除同步文件 IO、任务状态丢失或上游配额。不要首次上线就引入 Kubernetes；Docker + 受控发布 + 托管 PG/Redis + LB 也可作为扩展路线。构建前端时 Dockerfile 给 Node 4 GB 堆，构建机建议至少 8 GB 内存且与生产业务隔离；生产拉经过验证的版本镜像。

### 带宽与存储公式

- 小型 API：`RPS ≈ 在线人数 × 每人请求频率`。2000 人平均每 10 秒一次请求约 **200 RPS**。400 人平均每 5 秒轮询一次任务，额外约 **80 RPS**。
- 存储：`每日增长 = 活跃人数 × 每日图片数 × 图片均值 + 活跃人数 × 每日视频数 × 视频均值`。示例：2000 人各 10 张 × 3 MB + 2 段 × 30 MB = **180 GB/天**，30 天约 **5.4 TB**，还未加原始素材、缩略图、版本与备份。实际活动率低时同比降低。
- 视频分发：2000 人同时播放 4 Mbps 视频，峰值约 **8 Gbps**，不含协议开销。应用机器的 20–50 Mbps 公网带宽完全不够；这种场景需要 CDN。
- 下载内存：base64 大约将二进制大小变成 4/3，字符串/复制/JSON解析还会再增加占用。2000 个 20 MB 结果仅二进制就约 40 GB；即使不是同时驻留也应改成流式写对象存储，任务状态保存URL而不是base64。

## 4. 2000 个同时 AI 任务需要的配额

先测供应商真实平均耗时 `W`，以稳定状态 Little's Law `N = λ × W` 估算：`λ = 同时任务数 / 平均耗时`；RPM `= 60λ`；TPM 还要乘单任务token数。一次性 2000 请求突发要另外测，不能当成稳定吞吐。

| 仅作计算示例 | 2000 个在途任务要求 | 其它限制 |
| --- | --- | --- |
| 文本任务平均 60 秒，合计 4000 tokens/任务 | 约 33.3 任务/秒 = 2000 RPM，约 800 万 TPM | 上游通常区分输入/输出token与不同模型；用实际配额口径重算 |
| 图片任务平均 120 秒 | 约 16.7 任务/秒 = 1000 RPM | 渠道并发许可/排队容量、每次返回图片数量、下载带宽 |
| 视频任务平均 300 秒 | 约 6.7 任务/秒 = 400 RPM | 很多上游是异步任务，创建与查询各有配额；2000任务每5秒轮询会带来400 RPS |

若有 `c` 个上游执行槽位，一批 2000 任务的完成时间粗估 `ceil(2000/c) × W`，例如 100 槽位、平均 120 秒约 40 分钟，不含抖动/重试。此时平台可以接受 2000 **排队**任务，但不能把它宣传成 2000 个同时生成。

建议按模型/渠道建立共享 semaphore 与令牌桶，给每用户设并发和等待队列上限；超限返回排队状态/预计等待或明确 429，展示取消入口。队列必须有总容量保护，避免无界堆积。任务提交使用幂等键，供应商超时不能盲目重新生成，先查原任务状态。

资金预算：`每分钟模型成本 = 各模型任务RPM × 单任务实际成本`。文本成本按输入/输出/cache价格分别算；图片/视频按规格、张数、秒数和网关倍率算。未知模型组合和供应商价格时不能给可靠月账单。先设日预算、渠道预算、异常消耗告警和停止接收条件；“本地余额软检查”不能代替网关原子扣费。

## 5. 扩容必须先做的工程改造

| 优先级 | 工作 | 完成判据 |
| --- | --- | --- |
| P0 上线前 | 验证 PG/NewAPI 同库，TLS、域名、正确代理信任、密钥、备份恢复、镜像版本、监控 | 从空环境可部署；恢复演练通过；用户无法跨账号读数据；余额/扣费一致 |
| P0 容量基线 | 对登录、项目列表、画布列表、流式响应分别计时；收集事件循环延迟、池等待、慢 SQL | 给出 p50/p95/p99 与真正瓶颈，不能把浏览器无响应都归因于“服务器小” |
| P1 最直接提速 | 保留本次前端按需加载及余额池复用；列表分页；对 projectId/userId 查询按 EXPLAIN 检查索引；高频重复请求去重、预聚合进度 | 大用户数据集时列表 p95 达标；减少首次下载和网关非模型HTTP次数；缓存不过期权限 |
| P1 扩容阻塞 | 画布及 reseller JSON 迁到 PG（JSONB + 所有者索引 + 乐观版本/事务）；移走热路径同步IO | 2 个实例并发编辑有版本冲突检测，无文件扫描、无丢更新 |
| P1 任务可靠性 | OwnedTasks 替换成持久任务表 + Redis/BullMQ 等队列；API 与 worker 分离；任务结果存对象URL | API/worker重启后能查到任务并恢复；故障转移没有重复扣费；每渠道全局限制有效 |
| P1 文件与带宽 | 对象存储签名上传/下载、权限校验、缩略图后台生成、CDN与媒体Range支持 | 不经API搬运大文件；私人文件无法匿名获取；避免直接缓存私有响应 |
| P1 跨节点安全 | 验证码/失败计数/限频迁共享Redis；权限缓存有短TTL和封禁/会话版本失效机制 | 2 个实例之间换节点不会丢验证码或放大限频；封禁及时生效 |
| P1 实时消息 | Socket.IO共享adapter；保留long-polling则LB配置会话粘性；连接/消息配额共享 | 2000个真实隔离身份实时连接稳定、切节点不跨用户泄漏、重连能恢复任务 |
| P1 调度 | 团队现有PG锁保留；代理补扫/价格同步用独立scheduler或跨实例锁 + 幂等 | 多实例不会重复同步或多扣/漏记，慢任务不会重叠堆积 |
| P2 发布与运营 | 优雅停止接单、连接排空、worker优雅退出、数据库迁移单独执行、日志保留与分区/归档 | 滚动发布不丢任务；应用回退不用回退计费数据；容量报告持续更新 |

BullMQ 是改造建议，仓库目前没有完成接入。官方说明高并发 worker 主要适合异步 IO，CPU 密集处理需隔离进程；队列至少一次投递语义要求业务层自己做幂等。[BullMQ concurrency](https://docs.bullmq.io/guide/workers/concurrency)

Socket.IO 官方明确：HTTP long-polling 多节点要保证同一会话到同一节点；只用 WebSocket 可不要求这类粘性，但会失去 polling fallback。共享 adapter 解决跨节点事件，**不会自动共享 AI task Map、身份风控或画布文件**。[Socket.IO 多节点部署](https://socket.io/docs/v4/using-multiple-nodes/)

## 6. 第一阶段可执行上线流程（单应用实例）

1. 准备 Linux 主机、Docker Engine + Compose、域名和TLS证书。API 与 NewAPI/PG 走同地区私网；主机只公开80/443和受控管理入口，PG/Redis/NewAPI管理端口不直接暴露公网。
2. 使用现有 NewAPI 的 PostgreSQL，备份后在预发环境验证表兼容。NewAPI 是账号和扣费唯一权威，站长账户在 NewAPI 配置，不采用旧文档“SQLite自动建管理员”的流程。数据库账号要能迁移 `o_*`/`mc_*` 等业务表并读取实际依赖的网关表，权限收敛需按真实SQL验证。
3. 复制 `.env.docker.example` 为 `.env`，权限600，手工填配置：`NEWAPI_DATABASE_URL`、`NEWAPI_BASE_URL`、`NEWAPI_ADMIN_TOKEN`、`NEWAPI_DOCKER_NETWORK`、`XOI_NEWAPI_ONLY=1`。两个数据库连接变量若同时存在必须指向同一个库；本次余额优化后无需为了加速强制重复填变量。
4. 当前 Compose 仍要求 `XOI_ADMIN_PASSWORD` 环境变量，但示例文件未提供，且实际登录已转 NewAPI。**为兼容当前启动校验，在 .env 补一个随机高强度值；它不是实际 NewAPI 登录密码。**不要用 compose config 默认完整输出或日志复制来分享密钥。后续应清理这个遗留启动要求。
5. 反代与跨域变量在当前 Compose 环境列表之外，生产覆盖文件需显式加入。单层边缘 Nginx 示例见下文；域名更换为实际站点，proxy信任只设自己控制的代理IP。
6. 预发构建镜像并验证；生产拉固定版本镜像，不现场 `npm install` 补依赖。首次启动会执行 initDB/fixDB，预留迁移时间；扩容前拆出唯一迁移执行者。
7. `docker compose up -d --build`（试运营部署）；检查 `docker compose ps`，随后 `curl --fail http://127.0.0.1:10588/api/healthz` 和 `/api/readyz`。readyz失败先解决PG/NewAPI；不能把healthz成功当上线就绪。
8. 安装 `ops/nginx-single-node.conf.example`，改域名/证书位置，`nginx -t` 后reload；生产 Compose 将端口映射改为 `127.0.0.1:10588:10588`，只经Nginx进来。配置文件是**宿主机 Nginx**版本，不可直接放容器内照抄127.0.0.1。
9. 使用专门测试账户验收登录、画布保存、上传、SSE/Socket.IO、刷新恢复、支付/扣费链路，再跑第7节。收费模型测试在预算明确的预发渠道单独做。
10. 完成 PG 备份 + 媒体/画布/代理配置备份和恢复演练后才切流量。升级前备份并固定前一版镜像；运行中的 AI任务目前不能可靠跨重启恢复，单节点升级应先停止接收生成并等待在途任务结束。

生产覆盖文件中至少显式加（这些是非密钥示例；真实代理IP需确定）：

```yaml
services:
  xoi:
    environment:
      XOI_ALLOWED_ORIGINS: https://studio.example.com
      XOI_TRUST_PROXY: "172.20.0.1" # 示例：Docker侧实际Nginx来源IP，不要照抄
      XOI_DB_POOL_MAX: "8"
      XOI_DB_ACQUIRE_TIMEOUT_MS: "10000"
    ulimits:
      nofile:
        soft: 65536
        hard: 65536
    logging:
      driver: json-file
      options:
        max-size: 20m
        max-file: "5"
```

生产建议内存限制/预留按压测设定，避免 OOM 把 PG 一起带走。调整 nofile 还需检查宿主机与 Nginx：反代一个长连接至少涉及客户端与上游两条socket，不能把 worker_connections 简单当成最大在线人数。

NGINX 必须显式转发 WebSocket Upgrade/Connection，并让 read_timeout 大于 Socket.IO心跳窗口；SSE不应被响应缓冲攒到最后才显示。本次参考配置统一关闭代理缓冲，后续可对非流式路由单独开启。[NGINX WebSocket 官方说明](https://nginx.org/en/docs/http/websocket.html)

### 备份与回滚

- **PostgreSQL 同库整体备份**（同时含 XOi 和 NewAPI）；推荐托管自动备份与 PITR。独立保存角色/权限配置；只备份 data 卷无法恢复主业务/账户账本。[PostgreSQL 备份与恢复](https://www.postgresql.org/docs/current/backup.html)
- 文件卷备份包含 oss/canvases/reseller配置等，数据库引用和文件要有一致恢复时间点。不要把运行中的 PG 数据目录随意tar当一致备份。
- 试运营可暂定 RPO ≤ 24小时、RTO ≤ 4小时；2000用户商业上线目标建议 RPO ≤ 15分钟、RTO ≤ 1小时，是否达到由恢复演练决定。对象存储版本/保留与离站副本另计费用。
- 应用回滚用固定镜像版本；数据库兼容性必须先评审，不能用恢复旧整库来随意回退，否则会覆盖新账单和用户作品。

## 7. 压测和验收方案

本次脚本：`ops/loadtest/read-only.k6.js`。已通过 Node ESM 语法检查；当前机器没有 k6 和 nginx，未执行真实 k6 压测或 nginx -t。应在预发安装后执行这些检查，不能把本次语法检查当容量结果。固定路由只调用 `/api/login/self`、`POST /api/project/getProject`（实际执行SELECT）、可选 `/api/canvases`。不会登录/注册、新建项目、上传、创建生成或花费积分，也不会输出token或响应内容。读操作可能填充服务器缓存。**不要使用 k6 --http-debug、请求全量日志或导出授权头。**

先安装 k6，在独立压测机、隔离的预发库/测试账号运行。脚本默认为20VUs，最高允许2000；不是默认发起2000压力。测试用户应涵盖空项目/大量项目/大画布/媒体资产；只用同一个空账号会严重高估容量。

```bash
# 在当前终端安全读入临时JWT（不写入历史），不包含NewAPI管理员令牌
read -r -s TOKEN
export TOKEN
export BASE_URL=https://preprod.example.com
VUS=20 k6 run ops/loadtest/read-only.k6.js
# 再逐步升至50/100/200；不要直接对本机或生产起2000压力
VUS=100 INCLUDE_CANVASES=1 k6 run ops/loadtest/read-only.k6.js
unset TOKEN
```

大规模测试改用 `TOKENS_JSON`：一个JSON字符串数组，每项一个短期测试用户JWT，可以带Bearer前缀。由测试机秘密配置注入环境；不要把值直接写命令行、提交Git或打印。GET/POST通用API现有每用户每分钟1200次限制，令牌过少会把用户限流误判为服务器极限。2000不同用户测试应准备2000测试身份；Token映射按VU轮转，开放模型中的VU会被复用，不能据此声称模拟了固定2000条真实会话。

```bash
# TOKENS_JSON预先通过秘密配置注入后执行
VUS=2000 DURATION=30m INCLUDE_CANVASES=1 k6 run ops/loadtest/read-only.k6.js
# 对固定请求到达率独立验证，例如200RPS（duration是持续阶段）
MODE=rps RPS=200 VUS=600 DURATION=15m k6 run ops/loadtest/read-only.k6.js
```

VUs模式每次迭代约8–12秒思考时间，目标2000VUs通常约200RPS，具体取决于响应速度。闭合负载会在系统慢时降低到达率，故还要跑rps开放负载；若dropped_iterations大于0，可能是maxVUs或压测机资源不足，不能当容量通过。[k6开放与闭合负载](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/)

**这个脚本仅覆盖HTTP读路径，不验证真实Socket.IO、写入竞争、登录密码验证、支付、供应商生成或2000个持久连接。**其认证预检只验证第一项token，正式压测会验证所有被使用token的响应。

| 需要分开跑的阶段 | 数据/负载 | 建议验收目标（产品SLO草案，按实测修订） |
| --- | --- | --- |
| HTTP基线与峰值 | 50→100→200→500→1000→2000VUs，真实数据大小；200RPS持续30分钟、400RPS短峰 | 普通读API p95 <800ms、p99 <2s，HTTP及业务失败率各<1%，无持续池等待/内存增长；这也是脚本阈值 |
| 首屏/点击 | 冷缓存与热缓存、目标用户地区网络、常见设备 | p75 首屏可见 ≤2.5s，按钮本地反馈 ≤100ms；路由切换 p95 ≤1s（重编辑器单独记） |
| 登录 | NewAPI测试账号、多个来源IP、分段计时；尊重登录每IP10次/分钟及验证码 | 正常登录p95 <1.5s，失败返回清楚；不要为压测关闭生产风控。同一IP2000次登录不是合法容量测试 |
| Socket.IO连接 | 2000隔离测试身份，真实socket.io-client；只连接aiAssistant命名空间，不发送chat | 连接成功≥99%，持续60分钟，重连成功、心跳稳定；单用户有8连接上限，不能用单token造2000连接 |
| 编辑/保存 | 多用户、同画布多端版本竞争、同步大JSON | 版本冲突明确、无覆盖丢失、事件循环p99延迟<100ms作为初期观察目标 |
| AI模拟 | 可配置mock上游延迟/限流/超时，2000在途或排队；与真实生成隔离 | 接单p95 <500ms；平台区分排队与执行；不耗真实额度、不重复任务、重启可恢复（改造后） |
| 真正供应商 | 经批准的预算与明确配额，少量逐步递增、测TTFT和完成时长 | 单独展示供应商p95与错误率，不把供应商60秒生成当平台点击响应；不通过mock宣称真实2000模型并发 |
| 故障与发布 | 断worker/Redis/NewAPI，DB慢、应用重启、滚动部署 | 不重复扣费/生成，不丢完成状态，排队可恢复，健康探针真实反映依赖 |

压测期间监控：API CPU/内存/GC、Node事件循环、活跃HTTP/Socket、FD数、连接池active/pending与等待、PG CPU/IO/锁/慢SQL、网关上游429/5xx/TTFT、队列深度和最老任务等待、对象存储吞吐与CDN命中。目标稳定态 CPU <70%、内存 <75%、数据库连接保留≥20%余量；达不到时先定位瓶颈再扩容。最终容量报告要记录版本、机器规格、数据量、地域、负载、配额和全部指标。

## 8. 推荐推进顺序

先把新版引导、页面响应与登录提速这一版在预发跑通，完成单节点部署与只读基线；然后优先做画布数据库化、任务持久化、对象存储、跨节点身份/限流共享。做到这一层再部署双API/独立worker，跑完整2000在线与故障测试。2000同时AI生成作为独立上游容量项目推进，提前确认供应商并发和预算。

2000人目标可以规划，当前真实结论是：**已具备容器化与共享PostgreSQL基础，但多节点安全扩展和2000并发容量尚未验证。**
