# 画布模型与 new-api 统一

> 触发问题：「新建画布这里 没有和 newapi 进行统一啊」
> 现象：画布「配置与用户偏好」弹窗里是**本地直连 / OpenAI / https://api.openai.com / 已保存 0 个模型**，看不到网关里的模型。

---

## 一、根因（两层，都不是"少接了一个接口"那么简单）

**第一层：画布的模型来源不是 new-api，而是 XOi 自己的 `o_vendorConfig`。**

链路：

```
画布启动 → syncServerModels()  (atelier/src/xoi/server-models.ts)
        → GET /api/config       (backend/src/routes/canvas-stubs.ts)
        → 遍历 o_vendorConfig 里 enable=1 的供应商
        → u.vendor.getModelList(id)  ← 取「适配器文件里的 models」+「o_vendorConfig.models 列」
        → 整体替换画布本地渠道
```

`o_vendorConfig` 当时只有 **`agnes` 一个启用项**（直连 Agnes），表里**根本没有 `newapi` 行** ——
所以画布只能看到 Agnes 直连的模型，跟网关无关。

**第二层：`newapi` 适配器早已写好，但从未被启用。**

`backend/data/vendor/newapi.ts`（v2.0）是完整的 new-api 网关适配器：文本 `/v1/chat/completions`、
图片 `/v1/images/generations`、视频 `/v1/videos` 异步轮询 + `/content` 下载、语音 `/v1/audio/speech`，
还带 `fetchModels()`（从 `/v1/models` 拉清单并按名称分类）。它只是**没有对应的 `o_vendorConfig` 行**，
所以 `getModelList("newapi")` 永远不会被调用到。

顺带发现的第三个坑：`newapi.ts` 里的 `models` 字段**写着 6 个占位模型**（gpt-5.4 / claude-sonnet-4-5 /
gemini-2.5-pro / deepseek-v3.2 / doubao-seedream-4-0 / kling-v2-5）。因为 `getModelList` 是**并集**，
这些占位会永远出现在画布的可选模型里 —— 而站点根本没在网关上架它们，用户选中必然报错。**已清空**。

---

## 二、修法

| # | 动作 | 说明 |
|---|---|---|
| 1 | `data/vendor/newapi.ts` 的 `models` 置空 | 模型清单的唯一权威是**网关**，不是适配器文件里的示例 |
| 2 | 落 `o_vendorConfig` 的 `newapi` 行 | `inputValues = { apiKey: <站点级 sk- 令牌>, baseUrl: http://127.0.0.1:3000 }`、`enable=1`、`models` = 从网关拉取的 11 个模型（按能力分类） |
| 3 | `agnes` 行 `enable=0` | 直连供应商退出，全部调用下沉到网关（统一计费/倍率/渠道） |

模型分类沿用已在跑的 `agnes` 行定义（图片 `mode:["text","singleImage","multiReference"]`；
视频 `mode:["singleImage","text"]` + `durationResolutionMap`），新增的网关模型按名称关键词归类。

**生成侧为什么能自动切过去**：画布把模型以**裸名**下发
（`services/api/image.ts` 的 `model: modelOptionName(config.model)`），
后端 `canvas-stubs.ts` 的 `findVendorByModel()` 只扫 **`enable=1`** 的供应商、按 `modelName` 精确匹配。
`agnes` 停用后，同名模型只会命中 `newapi` → 请求走网关卡。

   （addVendor / updateVendorInputs / fetchModels / modelTest…）**既不在 `core.ts` 的白名单里、
   `app.ts` 也只加了中间件没挂路由** → 实测全部 **404**；Vue 主站与 React 控制台**都没有对应页面**。
   结果：供应商/模型清单目前只能靠落库维护（本次就是这么做的），
   「拉取模型列表」按钮那条路根本不通。要恢复得先挂路由、再补页面。
2. **`/api/settings` 仍是 404** —— 上游画布会请求它读「公共设置」；
   当前 XOi 的设计是**不走 remote 渠道**（模型由 `/api/config` 喂给本地渠道），
   所以留在 local 模式是符合预期的；只是那次失败会留一条未捕获的 promise rejection 噪音。
   若要彻底干净，可以补一个返回 `allowUserRemoteChannel:false` 的桩。
3. **`enable_online_topup` 仍为 false** —— 与合规无关，是**支付渠道未配置**（需要真实的收款账号/密钥）。

## 五、第二轮修复：弹窗还是没变（2026-10-03 03:20）

第一轮改完，用户复测**弹窗依旧是「本地直连 / 0 个模型」**。深挖后发现真正的架构坑：

**画布有「两套互不相通的 store」。**

- atelier 是独立应用：`main.tsx → @/router → @/pages/*`，用自己的 `stores/use-config-store.ts`
  （字段叫 `channels: ModelChannel[]`，persist 键 `infinite-canvas:ai_config_store:uu<uid>`）；
- 但 `pages/canvas/index.tsx` 是一行 re-export：
  `export { default } from "/…/infinite-canvas-main/web/src/app/(user)/canvas/page"`
  （注释写明 *"keep on the same upstream store/runtime"*），而 vite 别名对**上游 importer**
  会把 `@/` 解析回上游本仓 → **上游 store 是另一个实例**
  （字段叫 `localChannels`，persist 键 `infinite-canvas:ai_config_store` 无后缀）。

画布的配置弹窗（上游 `app-config-modal.tsx`，读 `normalizeLocalChannels(config)` 即 `config.localChannels`）、
节点生成、`isAiConfigReady` 全部挂在**上游 store** 上；而 atelier 自己的 store **只写不读**。
第一轮的同步喂错了对象，所以用户看不到任何变化。

### 修法

| # | 动作 |
|---|---|
| 1 | `server-models.ts` 现在**同时喂两份**：atelier store（`channels`，带 capability）+ 上游 store（`localChannels` + 平铺模型清单 + 各能力默认模型），上游那份用与 `pages/canvas` 相同的**绝对路径 import** 直连 |
| 2 | 上游 `isAiConfigReady` 原判定要求「本地渠道填了 baseUrl/apiKey」——XOi 的模型来自服务端、生成走账号代理，这判定永远 false 会挡住生成 → 改为「选中模型即可」 |
| 3 | 新增 `/api/v1/canvas/image-tasks*` 适配层（`canvas-stubs.ts`）：上游画布登录态下走"账号代理"，信封 `{code:0,msg,data:{id,status,progress,image_url,image_urls}}`，与 XOi 内部 `{task_id}`/`{status,result,error}` 两套约定 —— 同一套计费 + 供应商管线，两条路径两种信封 |

## 六、视频生成链路（2026-10-03 09:00-09:30）

上游画布的视频走**另一组约定**（services/api/video.ts，账号代理态）：
`POST /api/v1/videos` → 轮询 `GET /api/v1/videos/:id?model=`（信封 `{code,msg,data}`，data.status: processing|completed|failed + video_url）→ 成片 `GET /api/v1/videos/:id/content`（二进制）。

实现（canvas-stubs.ts 底部 v1 适配层，与图片同一套路）：
- 内部 POST handler 提成 `canvasVideoTaskCreate`，`/api/canvas-video` 与 `/api/v1/videos` 共用同一套计费+供应商管线；
- 字段映射：seconds→duration（数字）、size("720P")→resolution、aspect_ratio 直传、images/videos/audios 收敛成 URL 串数组、first_frame 降级为首张参考图；
- 创建响应包成上游信封（data.id=task_id）；轮询把内部 running/succeeded/failed 映射成 processing/completed/failed + video_url=result.url；content 302 到同源 /oss 落盘件。

**路由分工（重要）**：`/api/v1/videos*`、`/v1/video-tasks`、`/v1/async-result` **不进 ai-proxy 白名单**（先前误放，被抢去转发网关 → 契约不匹配 + 绕开 XOi 计费管线）——这些落 canvas-stubs 适配层走 XOi 管线（后扣模式：网关转发时实扣站点额度）；ai-proxy 只保留 chat/、responses、images/、audio/、tts/、models。

**网关 /v1/videos 的两个契约坑（vendor 适配器 newapi.ts 已修）**：
1. `seconds` 必须是**字符串**（Go 结构体 `.Alias.seconds of type string`，数字直接 400）；
2. `mode` 必填（"mode 不能为空"）——有参考图=reference、首尾帧=keyframe、纯文本=text。

**端到端实测（真实出片）**：
```
POST /api/v1/videos {model:"agnes-video-2.5-flash", prompt:"城市夜景延时摄影…", seconds:"5", size:"720P"}
→ {code:0,data:{id:"v_murpksid_sb788m",status:"processing"}}
轮询 ~2 分钟 → completed, video_url:"/oss/canvas/video/1/edf09739-….mp4"
/content → 302 → /oss 文件（3.9MB，ISO Media MP4 ✓）
```
网关侧任务状态机：queued → in_progress → completed（终态字符串是 **completed**，vendor 轮询判定一致）。

**计费口径**：billing.ts 已是**后扣模式** —— reservePoints 只做软校验（余额=网关 quota 折点，管理员不扣），capture/release 是空操作，真实扣费在网关转发时发生。o_points_ledger/reservation 表恒空属预期，不是 bug。
