# 后台与团队系统梳理及优化

日期：2026-10-11。原则：保留现有功能和账务口径，先改善导航、状态、操作反馈和读性能，再逐步完善协作模型。

## 现状判断

后台已经区分平台管理员和代理权限，团队已经有所有者、普通成员、可查看团队消费的成员，以及额度周期、算力池和消费记录。团队目前的核心是成员账号和预算管理。创作资源访问主要由 `resourceScope` 按用户归属校验，不能把现有团队直接称为“已完成项目共享协作”。`isolate` 存储字段也不能直接当作成熟的共享授权机制。

目前加入团队通过所有者创建新账号实现，不是给既有用户发送邀请。成员管理权限仅所有者持有；`can_view_all` 只增加消费查看范围。后续需要扩展角色与项目授权时，应在后端明确实现，不通过隐藏按钮代替权限判断。

## 本轮已实施

- 团队页按“团队概览 → 成员与额度 → 消费明细”分区，明确所有者与只读身份。
- 成员状态筛选、姓名/邮箱搜索、每页 25 条。2000 名成员不再同时渲染 2000 行。
- 明细使用时才加载；月份切换回第一页，刷新同时刷新消费明细，导出明确为“导出本页”，避免误以为导出全部记录。
- 改密失败保留弹窗及输入，保存等待、防重复操作、错误重试；额度和划拨金额增加有效值检查。
- 日额度、月额度、总额度分别统计。说明额度上限、实际钱包余额、团队池余额的关系，避免将不同周期的额度混加成“已分配金额”。
- 普通成员也能选择消费月份；只读查看者保留消费查看范围，不增加管理权限。
- 后台增加管理概览与团队入口，保留经典/新版菜单。手机侧栏可打开、关闭并正常跳转。
- 权限接口异常保持当前 URL，可原地重试；不会把服务错误当成“未开通代理”而跳走。
- 团队完整统计将每成员一次的周期消费查询改为批量聚合；2000 名成员统计固定 4 次读取。统计侧栏身份的 `summary=1` 改为轻量摘要，不扫描消费日志。普通成员仅读取自己的统计；明细复用一次成员读取。

此处修改的是读取方式和界面行为。日/月/总额的起点、消费日志口径、划拨与回收函数、实际模型扣费均保持原有规则。

## 下一阶段最值得做的改进

用户已确定：创作协作和额度管理都需要。应一起围绕团队项目设计，避免先做一套共享机制、再做一套独立预算机制。以下为待实施方案，不代表本轮已上线共享项目或项目预算。

| 优先级 | 具体问题 | 建议行为 | 完成标准 |
|---|---|---|---|
| P1 | 预算管理与项目协作尚未连接 | 建立团队工作区、项目成员表，区分个人项目与团队项目；现有个人作品保留个人归属 | 每个项目有明确所有者及参与者；跨团队访问被后端拒绝；移除成员后的资源访问按规则收回 |
| P1 | 角色只有所有者和消费查看权限 | 增加管理员、创作者、审核者、财务、查看者，并支持项目级授权 | 编剧能改剧本，财务能看账单但不能改内容，审核者能批准版本；后端逐项验证 |
| P1 | 加人只能创建新账号 | 支持邀请已有账号；邀请状态为待接受、已加入、过期、已撤销；保留创建成员账号 | 邮箱归属验证、有效期、重复邀请、加入其他团队冲突均有明确处理 |
| P1 | 额度补给不是完整的任务预算控制 | 每项目预算、成员预算、余额不足提醒；生成前估算并显示费用，明确超限后的行为 | 明确个人充值是否受团队额度限制、日/月重置时区；如需硬限制，生成前原子预留、失败释放、完成按实际使用结算 |
| P1 | 多人创建成员可能竞争席位，成员修改会全团队结算 | 成员创建时事务内锁定席位；成员额度调整只结算目标成员，周期补给分批处理 | 席位不超卖；单成员修改不会串行处理整队；同一用户不能重复挂在多个有效团队 |
| P2 | 算力池划拨和成员补给不在消费明细里 | 增加“预算流水”，使用现有团队 ledger 展示划入、提回、分配、回收；消费仍读取模型消费日志 | 钱包余额、团队池余额、实际消费可逐笔对账；操作含发起人、时间、对象、结果 |
| P2 | 没有清楚的创作审批与版本链 | 草稿 → 待审核 → 已通过 → 已制作；版本比较和退回原因 | 审核不触发收费生成；旧版本可查看，恢复有明确操作；已制作内容修改有提示 |
| P2 | 平台运营与代理经营混在同一长菜单 | 按运营概览、用户与团队、模型与任务、财务、内容、配置分组；代理只显示自己的客户和收益 | 保留旧入口可达；用户、团队、项目、任务、消费明细可相互跳转并保留筛选条件 |
| P2 | 配置与额度操作需要更好追溯 | 变更前后值、操作人、目标、时间、结果进入统一审计；配置编辑有未保存提示 | 模型价格/运营开关/成员权限变更可查；失败不能显示成功；重复提交不能重复发放 |
| P2 | 2000 人下日志查询与管理列表仍需要规模验证 | 日/月消费汇总、分页 API、按租户授权后缓存、任务队列观测 | 基于真实日志规模进行压测；监测 P95、数据库扫描量、队列等待、失败率；本轮 2000 名成员测试不等同 2000 人并发测试 |

## 建议最终操作流程

所有者创建团队 → 选择个人/团队项目 → 邀请成员 → 选择角色和项目范围 → 分配预算 → 创作和生成 → 审核版本 → 导出交付 → 查看预算流水和实际消费。

日常成员进入团队后应首先看到“我参与的项目、待处理事项、可用预算”；所有者看到“团队项目进度、成员、预算提醒”；财务看到“预算划拨、实际消费、异常项”。每个身份都能清楚知道下一步做什么。

建议分三步落地：

1. 先补协作基础：团队项目、邀请、项目参与者、后端授权。所有者管理团队，项目负责人管理该项目，创作者编辑授权内容，审核者审阅和批准，财务查看预算与流水。角色不应自动获得不相关的管理权限。
2. 再闭合生成费用：项目预算与成员额度同时约束团队付费任务；生成前显示预算和预计消耗，运行时预留，失败释放，成功按实际用量结算。日/月/总额、个人付费与团队付费须明确展示，是否允许切换付费来源应由团队规则决定。
3. 最后完善交付和运营：版本审核、退回原因、交付记录、预算流水、操作审计，以及后台从团队/项目跳转到任务与消费明细。异常重试要沿用同一任务标识，避免重复任务和重复收费。

这里的“先、再、最后”是实现依赖顺序；产品目标始终同时包含创作协作和额度管理。

## 验证与生效范围

数据库验证使用 PostgreSQL 临时表，在事务结束时回滚，不创建真实团队、不改真实余额。测试比较每日、每月、加入以来总额与原计算函数的结果，检查无消费成员、历史月份与当前额度分离、成员只读范围，以及 2000 名成员固定读取次数。

界面验证使用隔离浏览器和拦截接口的固定数据，不对真实用户改密或划拨资金。覆盖成员筛选、分页、改密失败重试、明细分页与月份切换、普通成员、手机后台导航、代理禁止进入平台运营、权限异常恢复。

前端构建和前后端类型检查通过，静态产物已同步到 `localhost:10588`。隔离浏览器针对该地址的更新产物通过上述交互验证；接口使用测试数据，真实多用户协作尚需后续联调。

后端读取优化需要在下一次后端重启/部署时启用；本轮未重启当前运行中的服务，避免中断进程内任务。
