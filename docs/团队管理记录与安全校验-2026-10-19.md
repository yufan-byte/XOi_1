# 团队管理记录与安全校验

本轮是对《团队空间布局与积分验收》的后续增量。旧文档描述上一阶段，不代表本轮后端已上线。

## 功能与权限

- 管理台团队空间继续复用管理台布局，不增加独立跳转。
- 新增“团队名称”设置，只有团队所有者可操作；不改变成员、积分或项目权限。
- 改名携带旧名称进行并发覆盖检查；旧页面提交返回 409，要求刷新。名称更新与操作记录在同一 PostgreSQL 事务提交。
- 新增“管理记录”，分为“积分流转”和“成员与设置操作”，每页 20 条。
- 积分流转直接读取既有 `mc_team_ledger`，不是第二本模型消费账。个人划入、转回、成员分配与回收分别显示方向及团队池余额。
- 新增成员、修改额度/消费查看权限、改密、停用、启用、移除、团队改名保留操作记录；历史事件不会伪造回填。
- 消费查看者仍是只读：没有改名和管理记录入口，后端也不允许查看所有者管理记录。不能通过 query/body 指定其他 ownerId/teamId。
- 手机上的团队标签支持横向滚动，保留可读文字，不强行压缩四个标签。

## 状态含义

- 已完成：操作回调成功，且结果记录写入成功。
- 结果待核对：回调报错，可能已经部分执行；不代表所有动作回滚或完全未发生。
- 处理中 / 结果未确认：意图已持久化，但还没有成功写入最终结果；进程中断、响应丢失等情况可能停留在此状态。

操作前必须先写入 durable intent；写不进去就不执行外部动作。操作成功但结果写入失败返回 502，提醒刷新核对而非自动重试。

移除成员原有“吞掉网关删除错误”的处理已移除。停用、回收、移出团队完成但网关账号删除失败时，明确返回部分完成、待核对，不记为全部完成。

这些记录提高可追查性，但不能将 PostgreSQL 和外部 NewAPI 变成一个原子事务。网关侧的幂等键、自动对账和管理员补偿处理仍需后续专项实现；目前不应自动重放状态不明的操作。

## 安全约束

- 成员接口严格校验真实布尔值、显式数字额度、周期、昵称、邮箱、密码长度及未知字段；字符串 `"false"` 不再被误当成开启权限。
- 管理记录按经过认证的团队所有者 ID 查询，每条成员目标也核验所属团队。
- 名称/昵称/额度/周期/消费查看权限是日志元数据允许清单；不保存密码、令牌、Authorization、完整请求或原始异常。
- 新增接口统一 `Cache-Control: no-store`；分页有服务器边界。
- 原 `isolate` 标记没有构成完整项目授权体系，所以禁止通过旧接口切换这个未完成能力；不修改现存值，不改变真实项目权限。
- 本轮未启用邀请链接、项目共享、跨团队资源访问，也没有修改管理员/成员角色定义。

## 数据库与发布

- 新增表 `xoi_team_operations` 与团队历史查询索引，不删除或重写旧表、成员或余额。
- 表初始化使用事务及 advisory lock，并纳入团队模块启动就绪检查。创建所需数据库权限未准备好时，不应视为就绪。
- 新前端依赖新 `/api/team/management`，需协调更新后端与控制台，不应只发布前端。
- 本地更新使用 `ops/local-service.mjs` 验证进程身份，获准后才重启 12121；生产服务器不在本轮范围。
- 如需回滚，保留审计表和已有记录。旧版本成员接口不会继续写本轮操作记录，因此不宜把旧版本长期混用作为完整审计方案。
- 本轮截至文档写入：代码与构建已准备，尚未更新本地运行服务；需完成页面验收并获得本轮重启确认。本文不是生产发布完成证明。
