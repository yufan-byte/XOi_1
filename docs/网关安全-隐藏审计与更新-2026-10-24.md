# 网关（new-api）安全：隐藏 · 审计 · 更新（2026-10-24）

> 回答三个问题：①别人都知道我们用 new-api，能不能藏起来？②new-api 审计出漏洞怎么办？③new-api 怎么更新？附带：安全检测机制说明。

---

## 一、先说结论（诚实版）

**"彻底隐藏用了 new-api"做不到**：XOi 透传网关的接口响应体形状（`{success,message,data}`）、错误文案、字段命名本身就是指纹。任何"伪装"都挡不住认真的人。

**但这不是问题，因为真正的安全边界不是"别人知不知道"，而是这三条**：

1. **网关本体外部打不到**：3000 端口只绑 loopback/docker 内网（生产 compose 已如此）——外部所有请求只能打到 XOi 代理层，攻击面 = 我们自己写并审计过的校验逻辑（已两轮审计 + 渗透实测）。**即使攻击者 100% 确认是 new-api，他也摸不到网关本体**，new-api 的管理端点（/api/user/manage、/api/redemption）、未公开接口、历史漏洞对他是不可达的。
2. **代理面是我们白名单出来的**：哪些网关端点可经 XOi 触达是显式写死的（log/self、user/pay、topup、model-catalog、v1 生成等），其余全部不可达。new-api 就算有 0day（比如某个冷门管理端点 RCE），**只要不在我们代理的白名单里，外部就无法触达**——这是代理架构相对"直接暴露 new-api"的本质安全优势。
3. **0day 应急 = XOi 层摘除**：若 new-api 某代理端点被曝漏洞，XOi 只需下线/收紧**那一个代理路由**（改一行挂载重启，分钟级），不需要等 new-api 出补丁。这是"出事了遭殃"问题的答案：有隔离层，可以精确止损。

## 二、能做且已做/建议做的"减指纹"清单

| 措施 | 状态 |
|---|---|
| 网关 3000 只绑 loopback，外部不可达 | ✅ 生产 compose 已固定 |
| `/api/status`（含版本号/系统名的典型指纹接口）不在 XOi 代理白名单 | ✅ 门禁白名单已注明不代理 |
| 网关登录页/UI 不对外（一切管理走 XOi 管理后台） | ✅ 架构即如此 |
| 响应体不带 `Server`/`X-Powered-By` 指纹头 | ✅ 建议在反代（Nginx/Caddy）统一摘除：`proxy_hide_header Server; server_tokens off;` |
| 错误文案中性化 | 🟡 部分（pay 失败分支已规整）；建议巡检代理面错误透传点，把含 "new-api" 字样的上游报错改写为中性文案（上线前做一轮 grep） |
| 网关容器名/内网域名不含产品名 | 🟡 部署时命名用中性代号（如 `gateway`），避免内网信息泄露连带暴露 |

## 三、new-api 的安全审计与我们的双层审计

**new-api 本身的审计机制有限**（开源项目，主要靠社区 disclosure）。所以我们的策略是**不依赖它的审计，自己有两层**：

1. **XOi 代理层审计**（已完成）：两轮代码审计 + 双账号渗透实测（身份提升/资金归属/SSRF/越权 25+ 项）；`check-console-routes --strict` 门禁持续保证"代理面=白名单"。
2. **运行时安全检测**（本次上线）：管理后台 → 安全检测（管理员可见，30 秒刷新）——登录爆破（同 IP 24h 失败≥10）、**管理员新 IP 登录**（历史基线对比，异地登录即告警）、**异常消费**（单用户单小时消耗超阈值，默认 500 积分=¥50）、**兑换频率异常**（疑似倒卡）。检测是提醒不拦截，处置走人工（用户管理停用 / 反代封 IP）。
   - 阈值环境变量：`XOI_ALERT_HOURLY_POINTS`；要接外发通知（邮件/钉钉/TG）时在该机制上加通知渠道即可。

## 四、new-api 怎么更新（含"出漏洞了"应急流程）

**日常跟版（建议每月一次）**：
1. 看 `calciumion/new-api` 的 GitHub Releases，重点关注带 `security`/`fix` 字样的版本；
2. 本地拉新镜像 → 起临时容器 → 跑冒烟（登录/充值档位/一次生成）；
3. 生产 compose 的 `NEWAPI_IMAGE` 改为新版本 digest → `docker compose up -d new-api` → readyz + 积分明细 + 兑换回归；
4. 出问题回滚旧 digest（compose 一行改回，秒级）。

**0day 应急（被曝漏洞当天的止损顺序）**：
1. 确认漏洞的**触达面**：在不在 XOi 代理白名单里？不在 = 无需动作（外部本来就打不到）；
2. 在白名单里 = 先摘除该代理路由（app.ts 注释掉对应挂载，重启，分钟级）；
3. 有补丁版本 → 走日常跟版流程升级；
4. 无补丁 → 保持摘除，评估业务影响，必要时开维护模式（console 运营设置，实时生效）。

## 五、与 XOi 自身更新的关系

- XOi 的更新走「发布中心 → 版本与更新」（rootOnly，GitHub Releases 检查 + 服务端脚本），与网关更新**互不影响**——两者是不同镜像、不同发布节奏。
- 网关管理员令牌（NEWAPI_ADMIN_TOKEN）只在服务器环境变量，前端产物已验证无泄露；即使 new-api 版本落后，攻击者也拿不到这个令牌。

## 六、遗留建议（按优先级）

1. **上线前 grep 巡检**：对 `backend/data/web/assets/*.js` 和后端错误透传点搜 `new-api`（不区分大小写），命中处改写为中性文案；
2. **反代指纹头摘除**：Nginx `server_tokens off` + `proxy_hide_header`，写进部署手册的 Nginx 配置段；
3. 安全检测接**外发通知**（钉钉/邮件 webhook），告警不再只靠后台刷新（机制已留好口）；
4. 管理员强制 MFA（new-api 支持两步验证的话开起来；XOi 层可加管理登录 IP 白名单）。
